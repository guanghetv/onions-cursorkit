# /auto-dev 小需求自动开发设计方案

> ⚠️ **此文档为初始设计草案，部分架构描述（后台 Runner、Cursor CLI Agent、云 Agent）已在实施过程中调整。**  
> **最终实现以 `plugins/common/skills/auto-dev/SKILL.md` 及其 `references/` 为准。**

## 1. 目标与范围

本方案定义一个用于小需求的自动化研发流程，入口命令为 `/auto-dev`。  
小需求指改动范围小、逻辑简单、可快速验证的任务，例如文案改动、新增提示、轻量配置调整。

核心目标：

- 只在首次触发时人工确认一次改动项目范围
- 确认后由后台 Agent 全自动执行，不占用开发者当前 Cursor 编辑器
- 每个命中项目独立完成开发、AI CodeReview、提交与 MR 创建
- 提测 MR 目标分支固定为 `develop`
- 最终仅等待人工审核 MR

不在本期范围：

- 大规模重构、跨域架构改造、复杂业务流程变更
- 自动合并 MR
- 自动发布到生产环境

## 2. 触发入口与总体架构

### 2.1 触发入口

- 统一入口命令：`/auto-dev`
- 支持输入：飞书需求链接或简要需求文本

### 2.2 组件划分

- **前台 Orchestrator（当前会话）**
  - 解析需求
  - 强制扫描当前工作区
  - 展示命中项目并收集一次人工确认
  - 生成 `run-id` 并投递后台任务
- **后台 Runner（Cursor CLI Agent / 云 Agent）**
  - 接管确认后的全流程自动化
  - 按项目并行执行独立流水线
  - 回写状态、日志、失败原因、MR 链接
- **运行状态存储**
  - `runs/<run-id>/meta.json`
  - `runs/<run-id>/events.jsonl`
  - `runs/<run-id>/project-<name>.json`

### 2.3 后台执行强约束

- `/auto-dev` 完成范围确认后，必须切换到后台 Agent 执行
- 执行过程不得占用开发者当前编辑器会话
- 开发者仅在阻断告警和最终汇总时需要关注

## 3. 强制工作区扫描与范围确认

### 3.1 强制扫描门禁（MUST）

- 未完成当前工作区扫描前，禁止进入代码改动阶段
- 扫描目标为工作区内所有注册项目（workspace 模式）
- 非 workspace 模式时，默认仅当前仓库为候选

### 3.2 命中判定

采用两阶段命中策略：

1. **快速命中**：项目名、目录、模块映射规则
2. **证据增强**：候选仓库内关键词/路径命中证据

### 3.3 判定结果语义

- **命中 >= 1 个项目**：展示命中项目列表，等待人工确认执行范围
- **命中 = 0 个项目**：提示“未扫描到匹配项目”，阻断自动化，不允许硬改

### 3.4 唯一人工确认点

确认卡片必须包含：

- 命中项目列表
- 每个项目的命中证据
- 预计改动类型（文案、提示、轻逻辑）
- 操作选项：确认全部 / 排除部分后确认 / 取消

确认后冻结项目范围。执行中发现新候选项目仅告警，不自动扩容。

## 4. 执行状态机（单项目/多项目通用）

每个项目独立运行，支持并行，互不阻塞：

`SCANNED -> CONFIRMED -> BRANCH_CREATED -> CHANGES_APPLIED -> LOCAL_VERIFY_PASSED -> CR_LOOP_PASSED -> COMMITTED -> MR_CREATED -> DONE`

关键门禁：

1. **分支门禁**：沿用 `create-feature-branch` 规则创建 feature 分支
2. **改动门禁**：仅允许小需求白名单范围，超范围改动进入 `BLOCKED`
3. **本地验证门禁**：最小验证集必须通过（lint/typecheck/受影响测试）
4. **提测门禁**：创建 MR 前硬校验目标分支必须为 `develop`

任一关键门禁失败进入 `BLOCKED`，并记录可恢复 checkpoint。

## 5. AI CodeReview 自动修复闭环

### 5.1 审查输入

- 当前项目 diff
- 小需求范围约束
- 项目规范与安全规则

### 5.2 分级与策略

- `Critical`：必须修复并复审
- `Major`：默认修复并复审（可配置阻断）
- `Minor`：允许带告警继续，但需写入 MR 说明

### 5.3 自动修复循环

最大 3 轮：

`review -> fix -> verify -> re-review`

退出条件：

- 无 `Critical` 且门禁通过 -> 继续提交流程
- 第 3 轮后仍有 `Critical` -> `BLOCKED` 并通知人工

修复安全护栏：

- 仅允许修改本次需求相关文件
- 越界改动立即阻断并告警

## 6. MR 创建与描述规范

### 6.1 MR 创建硬校验（MUST）

- 目标分支为 `develop`
- 分支为本次 run 生成的 feature 分支
- 本地验证通过
- CR 门禁通过（无未解决 `Critical`）

### 6.2 多项目产物

- 每个项目独立创建一个 MR
- 总控输出聚合结果与全部 MR 链接

### 6.3 MR 描述模板（MUST）

1. 需求背景（来源、目标、约束）
2. 改动内容（按模块/文件说明“改了什么、为什么”）
3. 影响范围（页面/接口/配置/文案触点）
4. 验证结果（lint/typecheck/test/关键日志）
5. AI CodeReview 结果（轮次、自动修复摘要、遗留 Minor）
6. 风险与回滚方案
7. 关联信息（需求 ID、run-id、跨项目 MR 链接）

## 7. 后台执行模型具体实现

### 7.1 模式 A：Cursor CLI Agent（V1 推荐）

实现方式：

- `/auto-dev` 前台确认后，启动 detached 后台任务
- 后台任务加载 `run-id` 配置并执行
- 周期性回写状态到 `runs/` 目录

优点：

- 落地快
- 依赖少
- 适合先在 2-3 项目场景验证

### 7.2 模式 B：云 Agent（V2 可选）

实现方式：

- 前台将 `run-id` 投递到云端任务队列
- 云 Runner 拉取任务并执行
- 结果回传后统一展示

优点：

- 不依赖本机持续在线
- 更适合高并发和长期运行

### 7.3 运行命令建议

- `/auto-dev status <run-id>`
- `/auto-dev logs <run-id> [project]`
- `/auto-dev resume <run-id> [project]`
- `/auto-dev cancel <run-id>`

## 8. 通知、恢复与可观测性

### 8.1 通知策略

仅在以下场景主动通知开发者：

1. 任务阻断（`BLOCKED`）
2. 所有项目执行结束（成功/失败汇总）

### 8.2 失败恢复

- 每个阶段写 checkpoint
- 支持从最近 checkpoint `resume`
- 避免已成功项目重复执行和重复建 MR

### 8.3 结果汇总

自动输出：

- 成功项目：项目名 + MR URL + 核心改动摘要
- 失败项目：阻断阶段 + 原因 + 人工建议动作

## 9. 验收标准（Definition of Done）

以下条件全部满足视为方案达成：

1. 入口命令固定为 `/auto-dev`
2. 触发后必须先执行工作区强制扫描
3. 命中项目确认后，全流程后台自动执行，不占用当前编辑器
4. 单项目与多项目都可独立自动建分支、提交、建 MR
5. 每个 MR 目标分支固定为 `develop`
6. AI CodeReview 支持严重问题自动修复，最多 3 轮
7. 超过 3 轮仍失败会自动通知人工接管
8. MR 描述内容结构化、可审阅、可追溯

## 10. 后续实施建议

- 先以模式 A（Cursor CLI Agent）完成 V1
- 在 5-10 个真实小需求上验证稳定性
- 再评估升级到模式 B（云 Agent）
