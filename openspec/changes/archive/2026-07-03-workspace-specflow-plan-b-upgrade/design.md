## Context

本变更基于方案 B：产品在 Cursor 中维护 `prd.md`（主）与 `prototypes/`（可选）。  
需求场景分为两类：

- 有原型需求：先原型，再产出 PRD
- 无原型需求：直接产出 PRD

本次设计目标是兼容两类需求，同时保持 `/pm-spec` 既有飞书读取能力不变。

## Goals / Non-Goals

**Goals**

- 提供独立的 `/pm-proto` 能力，专注原型生产
- 将默认产品路径调整为“`/req-new` 最小初始化 → `/pm-proto` 原型完善 → `/pm-spec` 补全 PRD”
- 升级 `/pm-spec`，增加 AI Review 并保留飞书读取兼容
- 在输入冲突时采用条件化优先策略（本地有实质内容则本地优先；空模板时飞书优先回填）
- 提供“对人可读”的 PRD 输出规范（富文本化块结构）

**Non-Goals**

- 不在本期实现飞书镜像同步（CI 与 webhook 服务均不落地）
- 不在本期扩展 metadata 复杂状态字段
- 不在本期维护与开发 change 的关联信息

## Decisions

### 1. `/pm-proto` 与 `/pm-spec` 分离

**决策**：新增 `/pm-proto`，不把原型能力继续堆叠在 `/pm-spec` 中。  
**原因**：原型生产高频迭代、PRD 结构化和评审是不同职责；分离后可兼容无原型需求并降低心智负担。

补充约束：

- `/pm-proto` 在生成前必须扫描当前工作区上下文（`workspace-repos.json`、需求目录、可访问前端项目）
- 涉及 UI 原型时，扫描重点覆盖样式规范、页面逻辑与核心交互链路
- 扫描后必须先进行脑暴澄清，再进入原型生成
- 原型已存在时默认走快速迭代模式，仅处理受影响模块
- 全量重构仅在显式确认后执行，避免每轮重做整页
- 每轮迭代先确认“保留/新增/删除/调整”变更单，再执行修改
- 每轮输出“本轮已改/本轮未改”摘要，并通过快速验收门后结束

### 2. `/pm-spec` 继续兼容飞书读取，且采用条件化优先

**决策**：

- 飞书读取优先使用 `lark-cli`
- `lark-cli` 不可用时降级到可用方式（如 feishu-mcp），并提示建议安装 `lark-cli`
- 本地 `prd.md` 有实质内容时优先本地
- 本地为空模板时以飞书文档为主回填生成标准 PRD
- 本地与飞书均有内容且冲突时，默认本地为准，并输出差异摘要供人工确认

**原因**：兼顾历史流程与方案 B 的主写入口。

### 3. AI Review 采用“高风险阻断 + 评分建议”

**决策**：

- 采用 P0 阻断策略（内容质量 5 条 + 可读性结构 3 条 + 用户场景 1 条，共 9 条）
- 迭代需求按 Step 3「本轮变更 MODULE 清单」聚焦深审，未在清单中的 MODULE 仅做一致性轻审
- 同时输出 0-100 五维评分；P0/P1 问题项全量列出（含位置锚点 + 可粘贴示例），P2 优化建议最多 3 条
- 先试运行两周再调规则阈值

**原因**：P0 保证质量底线；迭代聚焦深审 + P2 限 3 条控制反馈体量，避免全量重审导致 PM 放弃迭代文档质量。

补充约束：

- AI Review 详细结果（总分、维度评分、改进建议）外置到 `prototypes/ai-review.md`
- `prd.md` 仅保留“是否可开工”的结论性信息
- “飞书原文待补链”不作为评分项、不作为阻断项

### 4. 本期不落地飞书镜像同步

**决策**：飞书镜像同步从本期范围中移除，暂不实现同步服务。  
**原因**：本期优先解决“原型生成 + PRD 可读性 + PRD 质量门禁”三项核心体验问题，避免范围扩张影响落地速度。

### 5. PRD 采用“顶层阅读层 + MODULE 结构层”

**决策**：

- 顶层阅读层强调简洁，可选“关键变更摘要”
- MODULE 标题统一为 `MODULE-N: <模块名> [新增/修改]`
- 每个 MODULE 采用轻量 5 块结构：
  1) 需求描述
  2) 变更点
  3) 验收标准
  4) 模块特有边界与异常（可选）
  5) 引用（无原型时必须写“无原型（原因）”）

**原因**：兼顾机器可消费的结构锚点与人类阅读体验，避免模板过重导致执行阻力。

### 6. PRD 富文本化输出约束（强规则门禁）

**决策**：

- 可读性作为 `confirmed` 前置质量门禁，不满足则阻断 confirmed
- 默认开启面向 `Markdown for Humans` 的 WYSIWYG 友好输出
- 严格禁止大段文字：连续正文超过 6 行判定违规；未超 6 行但可读性差同样可判定违规
- 每份 PRD 必须包含 `## 关键关注（必填）` 区块（1~3 条 callout），重点信息不得仅出现在 AI Review 结论区
- 顶层“关键变更摘要”不强制、但若存在必须简洁
- 富文本元素采用“适量且必须”策略：
  - checklist、`[新增/修改]` 必开
  - callout 至少 1 个（关键关注区块）；Mermaid 按复杂度强制触发
- 复杂流程强制 Mermaid：存在分支逻辑，或流程步骤 >= 5 时必须提供流程图；迭代 + 模块级影响时允许在变更 MODULE 内局部图示
- 默认鼓励截图引用；无截图时仅提示建议补充，不阻断流程

**原因**：让 `prd.md` 的阅读体验更接近飞书文档，同时以强门禁保证团队愿意持续使用。

### 7. `/req-new` 改为最小初始化并引导原型先行

**决策**：

- `/req-new` 仅负责需求目录最小初始化与命名确认
- 初始化后默认引导产品先执行 `/pm-proto`，再执行 `/pm-spec`
- 不提示“飞书原文待补链”相关待办

**原因**：贴合产品真实工作流（先原型后 PRD），降低“空 PRD 先写”带来的心智负担。

## Architecture

### A. 内容生产链路

1. PM 执行 `/req-new`
2. 默认执行 `/pm-proto` 产出或迭代原型（可选带截图）
3. PM 在 Cursor 中完善原型与关键说明
4. 执行 `/pm-spec` 完成结构化 + AI Review + 人工确认
5. `prd.status = confirmed`

### B. PRD 生成与评审链路

1. `/pm-proto` 产出或更新原型，输出锚点并可选输出截图
2. `/pm-spec` 读取本地 `prd.md`、原型与截图引用、可选飞书输入；Step 3 确认需求类型与（迭代时）本轮变更 MODULE 清单
3. 输出结构化 PRD（阅读层 + MODULE 层，强门禁富文本：关键关注 callout、checklist、复杂流程 Mermaid）
4. 执行 AI Review（9 条 P0 + 五维评分）：按需求类型确定深审范围；P0/P1 问题项全量写入 `prototypes/ai-review.md`（含位置锚点 + 可粘贴示例）
5. 在 `prd.md` 仅保留 AI Review 可开工结论
6. 人工确认后设置 `prd.status = confirmed`

`/pm-proto` 内部执行策略：

1. 首次生成：全量扫描 + 基础骨架生成
2. 后续迭代：快速模式（局部扫描 + 局部替换）
3. 全量重构：仅在显式确认后触发

## Risks / Trade-offs

### [Risk] 模板过重导致填写负担

- **影响**：PM 可能绕开模板或填充质量下降
- **缓解**：采用轻量 5 块 MODULE 结构，移除优先级字段与强制冗余段落

### [Risk] AI 输出重新回到大段文字

- **影响**：可读性退化，团队不愿使用
- **缓解**：在 `/pm-spec` 输出约束中加入富文本化规则（列表/表格/callout/流程图优先）

### [Trade-off] 不在 metadata 记录详细评审状态

- **选择**：保持 metadata 轻量
- **代价**：跨会话追踪评分需要命令输出或后续单独存档
- **收益**：避免状态字段膨胀，降低流程负担

## Migration Plan

1. 新增 `/pm-proto` 技能与命令说明
2. 升级 `/pm-spec`，接入 AI Review 流程与兼容策略
3. 更新 PRD 模板与引用规范，纳入富文本可读约束
4. 小范围试运行两周（高风险规则命中率、可读性满意度）
5. 评估后再决定是否推进飞书镜像同步服务
