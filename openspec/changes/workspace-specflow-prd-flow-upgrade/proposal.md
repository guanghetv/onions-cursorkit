# workspace-specflow-prd-flow-upgrade

## 背景

- 产品工作区插件仍按 5 稿 / 9 稿推进，团队实际只维护一份飞书需求文档。飞书文档给人读和给 Cursor 开发读，`prd.md` 给 Agent 与测试用例使用，三端容易分叉。
- 飞书正文若用改色和历史句子表示变更，当前有效规则难以阅读。变更应留在版本表，正文保持当前结论。
- 原型带有占位文案和引导。发布后没有引导产品提交代码，也没有把基线变更通知到需求群。

## 目标

- 取消稿次。同一份飞书需求文档持续更新。第一次 `/prd-publish` 通过后 `prd.status=confirmed`，之后只前进基线。
- 原型、飞书文档、`prd.md` 由 Agent 对比差异，用户确认后再写入另外两端。
- 飞书正文和 `prd.md` 按《产品组 PRD 写作规范》写，不单设验收章。`/qa-spec` 从需求详情提取规则，并可直接读飞书链接；门禁只提示，不阻断生成。
- `/prd-publish` 成功后发短通知（有群才发），并引导产品提交代码。需求群可查询相对基线是否有未发布改动。
- 原型只保留核心页面流程和交互。
- Agent 写文档、改评论、查询现有实现时执行 `rules/agent-hard-rules.mdc`。

## 变更

- 去掉 `prd.stage` 的 v5/v9 稿次。基线由本地快照、飞书 `revision_id` 和版本表新行组成。
- `/pm-spec` 合并为单一写文档入口。主路径仍是先 `/pm-proto`，再产出 `prd.md` 与飞书文档。
- 任一端先改时，Agent 先给出差异判断，用户确认后才改另外两端。
- `/prd-publish` 成功即前进基线。漂移期间，除 `/qa-spec` 外的下游读上一版基线快照。
- 产品在工作区插件里只使用 `/prd-publish`。发布成功后的短通知和提交代码引导写在该命令里。`prd-change` 只保留给葱明-multica 的群内查询，不是产品命令。找到群后 POST 需求更新通知 webhook，由葱明发群。本机不发飞书消息。
- `/qa-spec` 增加飞书 CLI 读文档。未确认、一致性失败或相对基线漂移时仍生成，并在结果中提示。
- 原型生成去掉占位文案和操作引导。
- 已有内容的飞书文档禁止整篇覆盖。删除已有评论必须二次确认。查询现有实现必须先调用 CodeWiki `search_wiki`。

## 影响范围

- 页面/模块: `plugins/workspace-specflow` 的规则、`/pm-proto`、`/pm-spec`、`/prd-feishu-sync`、`/prd-publish`、`/qa-spec`、`/prd-consistency-check`，以及需求 `metadata.yaml` 的稿次字段。`/pm-spec-5` 与产品侧 `/prd-change` 命令删除。
- 数据/API: 无新业务接口。飞书文档使用 `lark-cli`；群消息使用当前登录用户身份。基线记录在飞书版本表和本地快照，不新增轮询接口。
- 权限/安全/资金: 不锁定飞书文档权限。无卡或无群时跳过群消息，发布仍成功。
- 兼容性: 已有需求目录里的 v5/v9 字段在读取时映射到「已确认 / 未确认」和最近一次基线快照，不要求产品重写历史文档。写作规范正文已在 `6702435`，本变更不重写该文件。

## 不做范围

- 不归档既有 OpenSpec / Trellis 遗留任务。
- 不做 10 分钟 revision 轮询，不用 webhook 搬运长变更。
- 不在插件里建飞书群。进「开发中」后的建群由飞书项目自动化完成。
- 不修改 Multica 远端绑定，不执行 `npm run sync -- --execute`。查询技能文本放在本插件，供后续人工同步。
- 不把 `notify_spec_published` 复用为需求基线变更通知。

## 验收

- 新需求不再出现 5 稿 / 9 稿阶段。第一次发布成功后 `prd.status=confirmed`，再次发布只追加基线，状态不变。
- 先改飞书或先改原型时，未确认前不写另外两端。
- 飞书文档已有内容时，同步命令清单中不出现整篇 `overwrite`。
- 删除已有飞书评论前，对话中有两次明确确认。
- `/qa-spec` 在未确认或漂移时仍产出用例，并带风险提示；给出飞书链接且 revision 与版本表一致时，能读文档生成用例。
- 有需求群时，发布成功后的消息只含版本、文档链接和变更 MODULE，不含全文。无群时发布仍成功。
- 新原型页面没有占位说明和给产品看的引导文案，主流程可走通。
- 产品询问现有功能实现时，规则要求先调用 `user-codewiki-mcp` 的 `search_wiki`。

## 风险与回滚

- 旧技能和模板仍写着 5 稿 / 9 稿。实现时按子任务替换入口，避免半套稿次和半套基线同时生效。回滚是恢复本变更前的技能文件，已发布需求的飞书正文不回滚。
- 基线快照缺失时，下游无法读到上一版。发布步骤必须先落快照和版本表，再把状态标成已确认。
- 群消息失败不得让基线发布失败。失败只记在发布结果里。
- Agent 禁令文件已写入工作区，尚未提交。若本变更回退，需单独决定是否保留该规则文件。
