# 审计结果 CSV 契约

文件名推荐：`telemetry-audit-results.csv`

## 目标

这张表现在同时承载三层信息：

1. 第二阶段审计结果
2. 接入适用性矩阵
3. 人工分配与执行跟踪

它既是后续 `telemetry:instrument-from-csv` 的输入，也是给人直接筛选、分配和追踪 MR 的主台账。

- `运行形态`

- `阻塞`

### 适用性矩阵字段

这些列统一使用：

- `适用`
- `不适用`
- `待确认`

注意：

- `适用性` 表达的是“该接入项对当前服务是否成立”
- 它不等于“当前是否已经接好”
- 是否已接好仍然看四个缺失字段与 `审计结论`

### `编程语言`

- 来源于飞书 Base
- 允许为空
- 第二阶段默认只处理 `Go / Node`
- 若为 `Python / 其他 / 空语言`，调度器可直接写入 `跳过`

### 四个缺失字段

四个检查字段统一使用：

- `是`
- `否`
- `未知`

### `执行状态`

推荐值：

- `待确认方案`
- `执行中`
- `待验证`
- `待提MR`
- `已提MR`
- `已完成`
- `无需接入`
- `已跳过`
- `阻塞`

说明：

- 允许为空
- 默认不要替用户写入“待分配”这类分派状态
- 若用户后续要自行安排负责人或批次，保持空白即可

### `验证状态`

推荐值：

- `未开始`
- `验证中`
- `验证通过`
- `验证失败`
- `无需验证`
- `阻塞`

## 结论映射规则

- 任一维度为 `是` -> `审计结论 = 发现问题`
- 四个维度全为 `否` -> `审计结论 = 通过`
- 依赖缺失、仓库不可用、检查器失败 -> `审计结论 = 阻塞`
- 本轮明确不执行 -> `审计结论 = 跳过`

## 边界说明

### 飞书原始状态 vs 接入适用性

第一阶段里的 `metrics_status`、`tracing_status`、`redis_metrics_status`、`pg_metrics_status` 只代表飞书服务信息里当前的勾选状态。

本文件里的 `链路初始化适用性 / Redis指标适用性 / Pg指标适用性` 等字段，代表的是代码层面的“该接入项是否适用于当前仓库模板”。

两者不能混用，也不要互相覆盖。

### Node 与 Go 的差异

- Node 服务不应被错误套用 Go 的 `observer / redis.MustRegisterMetrics / orm.MustRegisterMetrics` 路径
- Node 服务主要关注等价 tracing 初始化、Prometheus 指标暴露和中间件接入
- 是否需要进入某个接入项，应该同时看 `接入模板 + 适用性矩阵 + 缺失字段`

## 写入规则

- 每个 `服务名称 + 命名空间` 只保留一行最终结果
- 重跑时优先更新原行，不追加重复行
- `编程语言` 随同原行一起更新或补齐
- `推测框架 / 接入模板 / 运行形态 / 适用性矩阵` 属于可重算派生字段，允许调度器覆盖刷新
- `负责人 / 执行状态 / 验证状态 / Commit哈希 / MR地址` 属于执行跟踪字段，默认保留已有人工信息，不应被审计重跑清空
- 语言门禁产生的 `跳过` 行也属于最终结果，可被后续复用
- `检查摘要` 保留对人可读的短摘要
- `备注` 仅补充阻塞原因、异常说明或关键证据
- `执行备注` 用于记录分配、计划、验证或 MR 过程中的补充说明

## 调度器 / Worker 规则

- 单仓 worker 返回的单条结果必须能直接映射到本文件的审计结果列
- 调度器负责合并、去重、写 CSV，并负责派生 `接入模板 / 运行形态 / 适用性矩阵 / 默认执行状态`
- 审计缺失判断在 worker，不在调度器里
