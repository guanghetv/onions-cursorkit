# 单仓接入 Subagent Worker 契约

这个文档定义 `telemetry:instrument-from-csv` 内部单仓执行链路应该怎么做。

## 输入

至少读取当前行这些字段：

- `服务名称`
- `命名空间`
- `编程语言`
- `仓库地址`
- `接入模板`
- `运行形态`
- 全部 `适用性矩阵` 字段
- `Metrics缺失 / 链路追踪缺失 / Redis指标缺失 / Pg指标缺失`
- `执行状态 / 验证状态 / 执行备注`
- `统一分支名`
- `计划文档路径`
- `本地仓库路径`

## 执行顺序

1. 先读取当前行、计划文档和本地仓库路径
2. 计划生成后立即继续执行，不人工等待
3. 只在当前 `本地仓库路径` 内工作，不读取整份批量 CSV
4. 创建或复用统一分支
5. 只修改 `适用且缺失` 的接入项
6. 运行最小必要验证
7. 自动提交 commit
8. 自动创建或复用到 `master` 的 MR
9. 返回单条结果 JSON，由调度器负责回填结果表

## 计划文档建议结构

```markdown
# <服务名称> telemetry 接入计划

## 服务信息
## 当前审计结论
## 接入模板与适用性矩阵
## 本次要改项
## 本次明确不改项
## 验证方案
## 风险与回滚点
```

## 输出契约

单仓执行完成后，至少要能回填：

- `统一分支名`
- `计划文档路径`
- `执行状态`
- `验证状态`
- `Commit哈希`
- `MR地址`
- `执行备注`

建议 worker 最终返回严格 JSON 对象，不要混杂自然语言总结，避免调度器解析歧义。

### `执行状态`

只允许返回：

- `执行中`
- `待验证`
- `待提MR`
- `已提MR`
- `阻塞`

### `验证状态`

只允许返回：

- `验证中`
- `验证通过`
- `验证失败`
- `阻塞`

## 推荐返回格式

```json
{
  "服务名称": "study-plan",
  "命名空间": "7to12",
  "统一分支名": "telemetry-auto-20260420120000",
  "计划文档路径": "/abs/path/to/instrument-plans/study-plan__7to12.md",
  "执行状态": "已提MR",
  "验证状态": "验证通过",
  "Commit哈希": "abcdef1234567890",
  "MR地址": "https://gitlab.example.com/backend/study-plan/-/merge_requests/123",
  "执行备注": "已完成 tracing 与 metrics 改造；待确认项未自动落代码。"
}
```

## 重要约束

- 不要因为模板是 `Go-Kratos-Web` 就机械改所有项，只改 `适用且缺失`
- `适用性 = 待确认` 的项，默认写进计划和执行备注，不直接落代码
- 如果验证未通过，不要伪造 `验证通过` 或 `已提MR`
- 如果仓库已有未合并的 telemetry MR，要先在计划里写明是否复用
- 不要返回 `部分验证通过` 这类游离状态；拿不准时优先写真实的 `验证失败` 或 `阻塞`
- 如果 MR 创建失败但代码已推送，必须返回 `执行状态 = 阻塞`，并把原因写进 `执行备注`
- 如果 subagent 判断当前仓无法安全继续，应返回 `执行状态 = 阻塞`，并把原因写进 `执行备注`
- subagent 自己不要并发写总 CSV；只返回单仓 JSON 给调度器
- 单仓失败只阻塞当前仓，不应拖住整批其他仓继续执行
