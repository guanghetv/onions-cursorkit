# Telemetry 接入阶段 Checkpoints

## 阶段目标

基于第二阶段已经升级好的结果表，把“发现问题”服务推进到自动生成计划、自动执行改造、可追踪 MR 的状态。

默认执行模型是：调度器负责候选筛选、计划生成、prepare-repo、并发控制和总表写回；单仓实际改造由 subagent worker 完成。
默认退出条件是：已经没有可执行候选；不是“本轮先跑一批再停”。

## 进入条件

至少满足：

- `审计结论 = 发现问题`
- `接入模板` 已明确，不属于 `Unknown / NonTarget-Skipped`
- `执行状态` 不属于 `已完成 / 无需接入 / 已跳过`

## 状态机建议

- `待确认方案`：模板或适用项仍需人工确认
- `执行中`：已经开始创建分支或修改代码
- `待验证`：代码已改完，等待测试或验收
- `待提MR`：验证通过，等待提交 commit 和创建 MR
- `已提MR`：MR 已创建，等待合并或后续处理
- `已完成`：MR 合并或接入完成
- `阻塞`：仓库、权限、依赖或验证出现阻碍

如果你想自己安排负责人与批次，`执行状态` 可以先留空，不必预写默认分派状态。
计划文档仍然要生成，但默认只作为执行留痕，不作为暂停点。

默认 drain 语义下，这些状态属于终态，不应再进入下一轮候选：

- `已提MR`
- `已完成`
- `无需接入`
- `已跳过`
- `阻塞`
- `待确认方案`

## 计划文档最小要求

单仓计划 md 至少说明：

- 服务标识：`服务名称 / 命名空间 / 仓库地址`
- 当前模板：`接入模板 / 运行形态`
- 本次要改项：只列 `适用且缺失` 的项
- 本次不改项：列出 `不适用` 或 `待确认` 的项
- 验证方案：准备跑哪些命令、预期看到什么
- 提交与 MR：预期分支名、目标分支、回填字段

默认流程里，计划文档生成后应立即继续执行；除非该仓真实遇到技术阻塞，否则不要因为“等待计划审批”停住。

## Worker Dispatch 要点

- 调度器只生成 worker manifest，不直接进入业务仓改单
- 调度器每轮只取 manifest 中的 `dispatch_items` 做当前 wave
- 单仓 subagent 只处理一个 `本地仓库路径`
- subagent 完成后返回严格 JSON，再由调度器串行写回总表
- 建议并发 `2-4`，不要让多个 worker 直接并发写 CSV
- 每轮 merge 完成后要重新 `plan`，直到 `candidate_count = 0`

## 回填要求

每次推进后，至少更新这些列中的相关项：

- `计划文档路径`
- `执行状态`
- `验证状态`
- `Commit哈希`
- `MR地址`
- `执行备注`

如果某仓只完成了计划与仓库准备，还没完成改单，不要把它写成 `已提MR`；保持真实状态推进。
