# PRD AI Review Rubric

用于 `/prd-check` 的内容质量部分：高风险阻断 + 评分反馈 + 可定位改进建议。正文以《产品组 PRD 写作规范》为准。`/pm-spec` 改稿循环不自动跑这份评审。

落盘分层：

- 详细记录写入 `prototypes/prd-check-YYYY-MM-DD.md`
- 版本表对应行只在 `/prd-publish` 成功后追加。检查结论留在文末「文档状态」，不写进变更内容
- **风险预检**：由 `/prd-publish` 在检查前按新鲜度调用。报告里若已有结论，只写结论 + `prototypes/prd-risk-precheck.md` 路径，不内嵌规则明细，也不在本 rubric 里重跑预检

## 一、评审范围（先于阻断规则执行）

读取「需求概述」内嵌表中的 **需求类型** 与 **影响范围**，决定深审/轻审范围。

> MODULE 标题的 `[新增/修改]` 仅表示本次变更模块，不等于「增量/存量需求」。评审范围由需求类型决定。

| 需求类型 | 评审模式 | 深审范围 | 轻审/降级 |
|----------|----------|----------|-----------|
| **新增** | 全量 | 所有 MODULE + 需求概述 + 背景与目标 + 关键关注/回归（若有） | — |
| **迭代** | 聚焦 | **本轮变更 MODULE 清单**中的 MODULE + 关键关注（必要时核对概述目标句） | 不在清单中的 MODULE 仅做一致性检查；`影响范围 = 模块` 时复杂流程 Mermaid 可在变更 MODULE 内局部表达 |

**本轮变更 MODULE 清单**（迭代需求在脑暴确认，写入检查报告）：

1. **首选**：脑暴时产品确认的 MODULE 列表
2. **次选**：Feature List 中标注为本次变更的 MODULE
3. **兜底**：以上均缺失 → 全量深审，并注明「未提供变更清单，已降级为全量评审」

**评审范围说明**（写入检查报告开头）：

```markdown
## 评审范围
- 阶段：持续文档（无 5稿/9稿）
- 需求类型：<新增 / 迭代> | 影响范围：<角色 / 端 / 模块>
- 本轮变更 MODULE 清单：<MODULE-2, MODULE-3>
- 深审：MODULE-x, 需求概述, 背景与目标, 关键关注/回归（若有）
- 轻审：MODULE-z（一致性检查）
```

## 二、阻断规则（P0）

命中任一条即 critical，`/prd-publish` 不得写基线。不因这些规则去写 `prd.status=confirmed`。

### 内容质量（7 条）

1. 缺少明确目标或问题定义（概述或背景与目标中，只写「做什么」没写「为什么做」/目标）
2. 深审范围内关键 MODULE 的需求详情缺少可判断的规则、状态或异常。没有独立验收 checklist 不是失败
3. 范围边界冲突或明显自相矛盾
4. 深审范围内关键流程不闭环（成功/失败/异常路径缺失且业务需要）
5. 存在原型引用但路径或锚点无效（有原型需求场景）
6. 用户没有明确保留时，正文仍有未确认的 `[待定]` 或 `[待交互确认]`
7. 为补洞改写「关键关注/回归」展示序号，或把后续章节整段前移。保留背景与目标不是失败；删掉背景与目标反而违规

### 可读性结构（2 条）

8. 有复杂协作或回归风险时缺少「关键关注」或「回归范围」，或该信息只出现在版本表摘要里且无法定位
9. 深审范围内命中复杂流程条件（分支逻辑 / 流程步骤 >= 5）但未提供 Mermaid（迭代+模块级影响时允许在变更 MODULE 详情内局部图示）

### 用户场景（P0，仅深审 MODULE）

10. 深审范围内 MODULE 的详细说明完全缺少目标用户与使用场景

## 三、建议项（P1/P2，不阻断同步）

### P1（应修复，扣分并全量列出）

- **可读性告警（不阻断，必做）**：扫描契约区裸段落连续正文 >6 行、MODULE「详细说明」整格纯文字墙，或虽未超 6 行但主观难读
  - **本地报告** `prototypes/prd-check-YYYY-MM-DD.md` 必须含「## 可读性告警」：逐条位置 + 拆分建议
  - **飞书**只在文末「文档状态」里的 `prd-sync:check:v1` 写橙色摘要（约 N 处 + 报告路径），不要另开可读性 callout，也不要在飞书列明细
  - 无问题时报告中写「无文字墙告警」。校验行按是否还有其它 warning 决定 ✅ 或 ⚠️
- 有主场景但描述含糊，PM/开发仍可能理解分歧
- 业务需要但缺少边缘/异常场景
- 「回归范围」仅写「无回归」等歧义表述
- 表述、引用、局部可读性可改进但不触发 P0

### P2（可选优化，最多列 3 条）

- 体验优化、表述润色、非关键引用增强

## 四、用户场景透镜（深审 MODULE 必查）

每个**深审** MODULE 的详细说明须覆盖：

| 要素 | 要求 | 缺失处理 |
|------|------|----------|
| 目标用户 | 一句话（角色/权限/使用前提） | 完全缺失 → P0（规则 10） |
| 核心场景 | 主路径：触发条件 → 用户操作 → 预期结果 | 含糊 → P1 |
| 边缘/异常场景 | 至少 1 条（业务需要时） | 缺失 → P1 |

## 五、评分模型（0-100）

| 维度 | 分值 | 说明 |
|------|------|------|
| 目标与用户场景 | 25 | 仅评深审 MODULE |
| 范围与边界完整性 | 20 | 含背景与目标、关键关注/回归（若有） |
| MODULE 结构完整性 | 20 | Feature（若有）与详情 MODULE 对齐；图文对应 |
| 规则可判定性 | 20 | 规则、状态、异常能否直接判断；不要求验收 checklist |
| 可读性与引用质量 | 15 | |

P1 参考扣分：-8；P2 参考扣分：-3（总分不低于 0）

## 六、输出格式

### 写入 `prototypes/prd-check-YYYY-MM-DD.md`

```markdown
## 评审范围
（见第一节模板）

## 可开工结论
可开工 / 建议完善后开工 / 不可开工

## 总分
XX/100

## 可读性告警
无 / 共 N 处（不阻断）
- <章节或 MODULE-N>：裸段落 >6 行 / 说明整格文字墙 — 建议…
（飞书仅摘要+本报告路径，细节只写本节）

## 问题项
### [P0] <类别> — <位置>
...
```

**位置锚点**（语义标题；序号可随模板变化）：

- 需求概述（目标/为何做）
- 背景与目标 / 关键关注 / 回归范围
- 需求详情 / MODULE-N / 详细说明 或 图示

### 写入版本表

不要在 `/pm-spec` 之后、校验通过之前追加版本行。版本表行只在 `/prd-publish` 成功后追加。版本号从 `1` 起，每次成功发布加 `1`。回读序号 `R2` 只写入 `prd.baseline.revision_id`，禁止写进版本号。第一次发布的变更内容留空，正文不标红。之后每次发布，版本表这一格标红；正文里只给相对上一份已发布基线新出现或改写的规则句子加红色，已经标红的历史句子保持红色。这层颜色不是业务规则。检查时先去掉 `<span text-color="red">` 再比对，颜色差不算失败。不要把「校验：可开工」写进变更内容。风险预检为「需调整」或未预检时，不得追加版本行。

## 七、可读性约束

- 不单设验收章节；不要求验收 checklist
- MODULE 标题可带 `[新增/修改]`
- 复杂流程须 Mermaid（见规则 9）
- **长段落文字墙**：P1 告警（不硬拦）；明细进本报告「## 可读性告警」；飞书只在文末「文档状态」的 `prd-sync:check:v1` 写摘要
- 版本表只在 `/prd-publish` 成功后追加，版本号是追加前的 `R1`
