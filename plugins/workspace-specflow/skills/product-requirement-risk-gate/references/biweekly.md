# 逐次记录与双周汇总协议 v1.0

## 1. 落库与范围

每次预检保存运行记录及全部规则检查，用作审计和统计分母。每条HIT保存命中明细；待补信息的UNKNOWN不计已命中，但单列待判定需求。

至少保存三个逻辑对象（可以对应数据库表或同等持久存储）：

- 预检运行：run_id、需求ID/名称、业务负责人（如已提供）、可选产品负责人、PRD及快照版本、规则包版本、检查时间、提交时间、run_status、precheck_result、数据来源及保存状态。
- 命中明细：hit_id、关联run_id、需求/快照/规则ID及版本、L0/L1、触发时间、命中事实和证据、实际值与规则要求、整改要求、责任人及期限、审批升级标志。
- 状态事件：事件ID、关联对象、事件时间、操作人、业务接受/拒绝及原因、法务移交状态、法务最终结论引用、整改/复检/技术评审/发布状态、关闭原因及时间。

幂等键：命中明细采用“需求ID+快照版本+规则ID+规则版本”；重复运行同一组合不增加命中数，也不改首次触发时间。run_id唯一保存每次运行。后续复检仍关联该命中，并追加本次出现时间/运行ID。新快照或新规则版本生成新命中组合，历史保留。

没有HIT的结果也保存；已整改通过或取消需求不删除原命中。相同幂等键的内容冲突不能静默覆盖：保留异常并由产品检查快照是否漏升版本。

命中处理状态使用：待业务反馈、待整改、待复检、待法务处理、例外已批准且有效、已整改关闭、需求取消关闭、例外到期待重评。状态变更必须有依据。关闭按具体规则命中核验；同一需求仍有其他未处理命中时，需求不能整体标记“整改完成”。有效例外另列为持续跟踪，不混同整改关闭；到期重新打开并进入重评。一个需求的当前汇总状态按“到期/逾期待处理→待法务→待复检→待整改→待反馈→有效例外→全部关闭”取首个存在状态，同时保留所有明细状态。

数据库按角色控制访问。双周报使用业务需求级信息及证据链接，不复制手机号、密码、明文Token、兑换码或无必要的用户明细。手机号等使用脱敏关联标识。记录保留期限和删除策略由公司制度配置，不写死为永久。

## 2. 周期

- 时区固定Asia/Shanghai。
- 连续、互不重叠的14天周期，跟随产品双周迭代；按工作台配置的首个周期起点计算，不假定单双周。
- 工作台必须配置cycle_anchor、执行时间、report_destination、责任人及记录保留策略。具体迭代起点、数据库地址和飞书表ID本次未提供，接入时由产品配置。
- 时间窗采用[start, end)，正好在end发生的记录归下一期。
- 每个幂等命中组合以first_triggered_at归属新增命中周期。同一需求有多个版本命中，各版本明细保留；需求总数另按requirement_id去重。
- 后续变化按event_time计入“本期处理进展”；往期未关闭需求进入“存量未关闭”。不能只查本期新增而漏掉历史存量。
- 报表为截止end的快照。延迟数据保留事件发生时间和入库时间；补报生成同一周期的新报表版本，注明迟到数据及差异，不静默改已发布报表。

## 3. 完整性与计算

汇总前获取本期所有应检查的需求/提交清单、全部预检运行、命中明细、相关事件和历史未关闭明细。分页读全，校验工作台提交清单与保存记录，报告失败/缺失运行。查不到数据不等于零命中。

统一指标：

| 指标 | 算法 |
|---|---|
| 应检查需求数 | 本期应触发检查的requirement_id去重数 |
| 已检查需求数 | 本期至少一次run_status=complete的requirement_id去重数 |
| 未完成检查需求数 | 应检查集合减已检查集合；另列部分失败的需求 |
| 命中需求数 | 本期完整或部分结果中至少一次已确认HIT的requirement_id去重数 |
| 可比命中率 | 已检查集合中本期有HIT的需求数 ÷ 已检查需求数；分母0时为“不适用” |
| 新增命中需求数 | 本期first_triggered_at的命中组合涉及的requirement_id去重数 |
| 新增命中条数 | 本期first_triggered_at的唯一命中组合数 |
| L0/L1数量 | 分别统计新增命中条数及去重需求数；同一需求可能同时出现在两级，不将级别需求数相加充当总数 |
| 各规则/场景 | 命中组合数与去重需求数分别列；多场景说明可重复计入分组 |
| 整改/例外/移交数量 | 需求级按截止end的当前状态互斥归类；另外保留事件次数，不能混用 |
| 本期整改完成 | 本期关闭事件有新版本复检通过等凭据，按需求去重；“接受整改”不等于完成 |
| 逾期 | 有明确期限且截止end未完成；未设置期限单列，不自动视为逾期 |

曾命中后本期整改通过的需求仍计本期命中；当前状态另列。待补信息及部分失败单独展示；部分运行中的已确认HIT不丢失，但不混入完整检查命中率的分子。

报表生成前必须核对：对应运行版本的规则集合完整（当前37条，历史版本按原集合）、预检与命中记录关联完整、幂等键无重复、周期无重叠、记录分页完整、应检查清单覆盖。有数据缺口则report_status=incomplete，保留可确认明细和缺口，不发布为完整零命中报告。零命中且覆盖完整时仍保存“本期0命中”的完成记录。

## 4. 固定输出

1. 报告标题、周期、时区、生成时间、截止时间、版本、数据覆盖及complete/incomplete状态。
2. 指标：应检查、已检查、未完成、命中需求数、命中率、L0/L1、待判定。
3. 全部本期新增命中明细：需求、负责人、PRD版本、规则、证据、整改、反馈、移交、当前处理、计划上线时间。
4. 本期处理进展：往期及本期命中在本期发生的整改、拒绝、例外、关闭和重新打开。
5. 存量未关闭/逾期清单及责任人。
6. 高频规则、重复问题和规则优化建议；建议不自动修改规则。
7. 数据缺口、失败运行、待补录和下期跟进。
8. 原始明细查询链接、保存记录ID、回读核验结果。

主台账在产品工作台数据库；预留固定飞书Base同步映射，但未配置表ID及授权时只标记not_configured，不创建新表、不虚构链接。外部同步/通知状态与数据库保存状态分开。没有明确通知配置时只保存汇总，不发送消息。

## 5. 调度与失败

由产品工作台服务器在每个周期结束后执行，传入明确start/end。运行编号和“周期+版本”唯一；同一期重试不重复生成报告。保存结果后回读验证周期、明细数量、关键指标和完整性状态，才标记saved_verified。

失败保存failed或incomplete及原因，由产品设置有上限重试和失败提醒。下一次运行先检查最早未完整周期，逐期补跑；已完整周期不无故重跑。不能仅依据定时任务已开启就宣称汇总成功。Skill缺少数据库或调度能力时仍可根据完整导出数据生成人工报告，但明确尚未实现自动记录/自动双周汇总。

DEFERRED为非阻塞后置项，不计待补信息或命中；业务必填UNKNOWN才进入待判定。历史删除或本次编号调整均不删除历史命中，不将编号变化记为业务整改完成。历史按原规则版本+编号归属；跨版本按rules.json的rule_id_migrations映射规则内容，不把旧版额度规则R-B端-03与当前收权规则R-B端-03合并。仅改编号不关闭旧命中、不修改first_triggered_at，旧规则内容已删除时另记规则变更依据。
