# 输入输出协议 v1.1

## 1. 当前阶段及信息来源

本Skill是业务方案进入评审前的风险预检。需求事实、方案和补充回答仅由业务提供；不要求产品或研发参与填报，不要求完整PRD。业务必填齐全即可生成预检结论；技术细节、平台元数据和生产证明缺失不阻塞。平台接入、后续技术评审及发布门禁属于独立阶段。

## 2. 必须提供与非必须提供

### 每次必须：由业务提供，优先从正文抽取

| 业务必填 | 所需粒度 |
|---|---|
| 方案目的及目标指标 | 做什么、希望改善什么；可以是非财务指标 |
| 计划上线/执行时间 | 日期或明确窗口；确实未定则记待补，不猜日期 |
| 正常业务规模 | 人群/操作主体、预计量及对应周期 |
| 权益及操作总上限 | 是否有；有则说明量及口径，无则如实记录，不强行改成有 |
| 是否公开传播、是否可分享 | 是/否及涉及对象 |
| 单个操作主体允许次数 | 操作主体、次数/数量及周期；单人单次是有效答案，不强行展开为多个角色 |
| 单次权益或操作内容 | 类型、时长/金额/数量、重复领取或叠加方式；不涉权益时明确实际操作 |

### 条件必填：仅在真正影响业务规则判定时补问

- 权益性质不明：原订单应得但漏发、免费/低价、额外赠送或付费赠送；历史购买不能自动证明履约补发。
- 资格及审核范围不明：谁能参加、由谁确认；“业务负责人确认固定历史订单名单”足够，不索取学生明细、订单导出或技术校验过程。
- 数值阈值适用：业务决定的价格、权益天数、分享有效期等。规则有明确数值且正文未提供才补问，不猜值。
- 操作机制不明且影响适用性：业务员工自助后台还是研发一次性执行；是否给业务主体新增/改变权限；是否涉及兑换、第三方、退款、分享等。只问实际场景，不要求接口清单。
- 业务可决定的控制有无会影响判定时，可问一次概括问题，例如是否验证手机号、是否限制重复领取。已有明确答案不再拆问实现。

### 非必须：不得作为补件或“待补信息”的依据

- 产品/研发负责人、完整PRD及版本、工作台需求ID、审批流或数据库配置。运行ID和本地快照可自动生成，不冒充真实平台编号。
- 接口清单、登录态/Token类型及有效期、签名、原子性、并发重试、限额落库、服务端实现、日志字段/查询维度、设备校验、老接口技术清单、测试/生产日志和配置截图。
- 如何把一次性名单上限换算或实现为角色单次/单日/单月额度；异常告警阈值、暂停实现、回滚技术细节。
- 技术评审结论、发布证据、研发排期和人日、收益金额、法务M1—M6资料。申请例外后再按独立流程补法务所需信息。

不能把“可选”理解为忽略已明确违规：例如业务主动提出无鉴权即可改权益、可伪造参数或明确绕过风控，仍按对应规则HIT。

## 3. 设计承诺与阶段判定

先检查适用性，再给每个check增加requirement_stage=business_required/later_stage、blocking_in_precheck及证据引用。规则的技术checks用于后续核验，不是业务逐项问卷。保存value（未知为null）、data_status（provided/missing/unavailable）、evidence_type（business_fact/design/system_verified）、source_reference和覆盖范围。只有业务明确确认无法提供才用unavailable。

- **MET**：业务已描述满足该条件的相关方案或限制。按design满足，无需实现细节和生产证明。概括承诺仅覆盖它实际表达的义务，不扩展至所有规则。
- **HIT**：适用场景已确认，业务明确的数值或方案与规则冲突。已知不符合优先，不因其他字段缺失隐藏命中。缺失绝不能当作false。
- **UNKNOWN**：缺少业务必填，确实无法判断；记录具体问题及必要性，blocking_in_precheck=true。
- **DEFERRED**：仅缺非必须技术实现或其适用性，留待后续正常评审；blocking_in_precheck=false，不要求任何人在本次补齐，不假称已技术满足。
- **NOT_APPLICABLE**：有事实支持不适用，保留原因。无证据的技术范围不能硬判不适用，使用DEFERRED。

每条规则汇总优先级：已确认HIT，其次业务必填UNKNOWN，再次DEFERRED；其余适用项满足为MET，无适用项为NOT_APPLICABLE。整体：任一HIT→需调整/ADJUST；否则业务必填缺失→待补信息/SUPPLEMENT；否则→规则预检通过/CONTINUE，即使存在DEFERRED。独立记录provisional与保存状态，不把未接工作台等同业务待补。

### 本次测试纠偏及通用边界

- “固定名单、仅一个人、单次、仅某一天、总量12000”已构成本次额度的业务设计，可令R-B端-02额度条件MET/design；不要求另提角色周期额度、锁名单、幂等或强制执行实现。预计量大不自动HIT，原文无具体额度阈值。
- 同一说明中“不做限制”若指不另建员工额度体系，但已有上述边界，不截取这四字生成HIT；明确允许无限新增/重复发放且无任何边界时才判额度不符合。真正自相矛盾且无法结合上下文消解时仅问冲突点。
- 异常预警暂停未说明属于后置设计细节，DEFERRED，不因此要求业务补件；已概括承诺异常预警暂停则MET/design；明确取消全部异常预警暂停仍HIT。
- R-B端-03仅在本需求涉及业务员工/学校/角色的权限生命周期时检查。研发一次性执行且明确不新开业务权限，不强加新授权及收权方案；不等于豁免现有生产权限管理。
- 当前R-B端-01是B端可分享链接有效期规则；v1.1.0曾删除的旧版同编号规则内容仍不恢复。历史按版本+编号识别；旧版02/03/04分别对应当前01/02/03，映射见rules.json。不要把历史删除说明当作当前R-B端-01不适用。
- 免费活动的7天规则不适用于已明确的原订单漏发权益；适用赠送活动时30天仍HIT，只有>30天触发管理层特别审批。
- 业务提供精确技术数值时保留eq/lte边界：操作Token≤10分钟、会话≤24小时；不主动向业务索取此类非必须数值。负数/非有限值或单位不清不得判满足。
- 无分享、无相关第三方或无拉新机制时排除对应子条件；不扩展所有普通复购为限购违规；G-*旧保护不生成业务任务；治理规则只随真实治理变更触发。

## 4. 输出及后续流程

正文面向业务：结论；命中规则及业务方案调整方向；必要业务补件（没有则省略）；下一步。不得提出“整改由研发承接并补实现方案”作为本阶段完成条件。

必填齐全无命中：输出“规则预检通过，可进入正常方案评审；不等同技术验证或上线批准”。有命中：请业务调整方案或说明不能调整的原因，再复检/申请例外。后置实现细节仅保存在later_stage_items，必要时一句说明由后续正常评审处理，不将清单变成当前补件。

delivery_test未接确定性执行器时provisional=true，但可以给出上述三类辅助结论。production规则版本和运行完整性必须核验；错误进入RULE_REVIEW/RETRY，不伪造通过。

以上为字段模板，不是完整示例结论。规则明细必须包含全部37条扫描结果。每条rule_checks包含rule_id、rule_version、level、applicability、适用理由及证据、result（HIT/MET/UNKNOWN/DEFERRED/NOT_APPLICABLE）、每个check的输入/比较值/判定、命中证据、整改要求、责任角色、compliance_basis及technical_verification_pending。

run_status为complete/partial/failed；技术故障或规则缺失时precheck_result可为null，provisional=true，workflow_route=RULE_REVIEW或RETRY。业务事实完整性不足但规则检查正常执行可以是complete及“待补信息”。保存状态另列，避免将“评估成功”混为“入库成功”。

下一步路由：CONTINUE、SUPPLEMENT、ADJUST、LEGAL_LOSS_ASSESSMENT、D_OR_SPECIAL_APPROVAL、RULE_REVIEW、RETRY。前三类业务预检结果与这些后续路由分开保存。

### 产品正文：可直接转发业务

正文只展示影响下一步的事项，以清晰、明确、易懂为原则：

1. **评估结论**：需调整、待补信息或预检通过，紧接一句主要原因。辅助预检、运行异常或尚未提交等重要限制简短说明。
2. **需处理事项**：全部已确认命中逐项展示规则编号、名称、等级、规则原文、判定依据、整改要求及业务可决定的调整方向。这些内容必须直接展示，不得仅放折叠详情或附件。用需求原话或短来源标注支撑判断；推断明确标注，缺信息写待确认，不能算命中。待判定规则与已触发规则分开，每项问题就近列所需补充，避免重复。
3. **下一步**：按下方阶段给出具体动作、责任方和提交对象，不用“走法务流程”等泛指。
4. **请业务回复**：只列业务需要决定或补充、可以直接回答的问题；没有则省略，已回答的不重复索取。

正文不罗列全部37条结果或不适用规则。完整检查、全部缺项及来源、版本、保存状态保留在结构化记录和可访问详情中。本次不向产品或研发索取材料。技术实现细节仅放later_stage_items，不作为当前任务或业务补件；工作台元数据缺失不阻塞业务结论。UNKNOWN仅用于缺少业务必填；后置细节使用DEFERRED，不能混作业务缺项。

整改要求须具体可执行；规则未规定具体额度或数值时，由业务提出，AI不自行创造阈值。

### 下一步：按当前阶段输出

- 需调整、业务尚未反馈：要求业务确认整改方案或说明不能调整的原因。
- 缺信息：一次性列明业务需补的具体内容。
- 接受整改：业务补充调整后的方案，由Skill生成新快照并重新预检，不等待产品提供新PRD。
- **业务明确拒绝整改，但尚未要求制作申请包或提交例外评估**：直接询问“业务已确认不接受调整，是否需要制作例外评估申请包？”保留拒绝反馈和原命中，不宣称已生成或已提交。
- **已明确要求制作申请包或提交例外评估**：直接制作完整申请包，不重复询问是否制作。
- **申请包已生成**：提供可访问文件链接，并明确输出“例外评估申请包已生成，请将申请包提交至‘法务助理机器人-业务灰产风险损失评估’，进行例外评估。”不得仅写“由产品提交法务例外评估”。没有提交能力时简短标记未提交。
- 预检通过：继续正常产品评审，不等同技术通过或发布批准。

申请包制作询问是产品交互步骤，不改变规则等级。L0仍硬阻断，申请包明确D类或专项审批，不得因机器人名称含“损失评估”而转为普通收益比较。指定名称不等于已配置接口或获得发送授权；用户明确要求实际发送且有工作台配置与权限时才执行提交。有接收凭证后才能报告已提交，此时指引等待该机器人评估结果，不再重复要求人工提交。

## 6. 法务交接包

包括handoff_id、原运行及需求ID、快照/PRD链接和版本、全部命中及L0标记、业务拒绝整改的原话/原因/时间/确认人、申请例外内容、现行控制及证据层级、整改记录、权益/价格/规模/周期/渠道等已知事实、收益及来源、明确无法提供项、待技术核验清单、审批升级标志和规则版本。

L1移交loss_assessment；L0移交D_or_special，不能沿普通收益比较放行。机器人接口可用且工作台已配置授权时执行并保存接收凭证；否则handoff_status=pending，附可直接转交正文。A/B/C/D、评估金额和审批结论仅回收自法务流程，不自行填充。

## 7. 原始记录与状态更新

需求快照、预检结果不可静默覆盖。业务反馈、法务交接、整改、技术核验、最终处理分别保存追加事件：event_id、requirement_id、snapshot_version、关联run/hit/handoff_id、event_type、event_time、actor、依据引用、变更前后状态。

应用角色授权：业务提交事实和反馈；产品提交/复检及跟进；技术团队核验控制；法务/风险及相应审批人处理例外；规则责任人发布规则。AI生成建议不冒充人员确认。
