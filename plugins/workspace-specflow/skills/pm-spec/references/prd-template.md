# prd.md 模板

正文写法以 `plugins/workspace-specflow/references/产品组PRD写作规范.md` 为准（来源 [产品组 PRD 写作规范 V1.0](https://guanghe.feishu.cn/docx/Cqtqd9BxJoUYAFxbXFocp2qYnWd)）。

`prd.md` 是持续更新的工作稿。下游在第一次 `/prd-publish` 成功后读基线快照；漂移期间不把未发布正文当成已发布需求。章节定位以 **语义 unit + 标题关键词** 为准（见 `prd-feishu-sync/references/chapter-map.md`），序号仅展示/兼容。

旧飞书七章模板链接仅作兼容参考：https://guanghe.feishu.cn/docx/S38Id4fxAofdz8xsWCVcRkHjnHg。新文档以写作规范的组织方式为准，不为凑齐旧七章增加空章节。

## 结构约束

- **组织**：需求概述 → 版本及进度跟踪 → 背景与目标（含本次范围）→ 需求详情。关键关注、回归范围、Feature List、关联材料与待确认项、数据观察与发布约束只在有内容时加，不进空骨架。
- **背景与目标保留**：本地与飞书都保留。不再做「9 稿删背景/价值」。
- **不单设验收章**：MODULE 详细说明写规则、状态和异常。不把同一规则再写成验收 checklist。
- **不要求套用**「功能说明／交互说明／补充规则／验收标准」四段式。
- **工作区补充**：有复杂协作或回归风险时保留「关键关注」「回归范围」。没有内容时不硬凑空章。
- **Feature / MODULE**：多模块时可用 Feature 清单对齐 MODULE。单模块小需求可直接写需求详情。
- **原型**：`prototypes/` 引用与 MODULE 锚点保留；无原型时写明原因。
- **序号**：已有旧稿不得为补洞重排「关键关注 / 回归」，也不得把它们后面的章节整段前移。新文档不写「一、」到「七、」，按标题定位。

## 完整结构

标题用需求名，不加 `【】`，不加 `PRD`。没有内容的章节不要出现。关键关注、回归范围、Feature List、关联材料、数据观察与发布约束只在确认有内容时另加，不写「本需求无额外……」，也不预置空的「待确认」。

版本号规则只留在本文件的「要点」，不要抄进 `prd.md` 或飞书正文。

~~~markdown
# <需求名称>

## 需求概述

| 项目 | 内容 |
|------|------|
| 需求类型 | 新增 / 迭代 |
| 影响范围 | 角色、端、业务模块 |
| 原型情况 | 有原型 / 无原型（原因） |
| 建议阅读顺序 | MODULE-1 → MODULE-2 |

用一段话讲清：谁在什么场景遇到什么问题，本次要改变什么，上线后希望看到什么结果。指标有依据才写。

（复杂流程时在本节末尾附 Mermaid 主流程图）

## 版本及进度跟踪

| 日期 | 版本号 | PM | 变更内容 | 对应 spec / demo |
|------|--------|-----|----------|------------------|
| YYYY-MM-DD | 681 |  | 发布基线；变更 MODULE-1、MODULE-2 | snapshots/prd-baseline-YYYY-MM-DD.md |

## 背景与目标

说明为什么做、做到哪里。可按「背景」「目标」分小节；不要删掉整节。

### 背景

- 当前现状：
- 当前问题：

### 目标

- 本次要改变什么：
- 预期结果：

### 本次范围

- 涉及角色 / 端 / 模块：
- 容易混淆的边界（只写必要的，不罗列大量无关「不做」）：

## 需求详情

### MODULE-1: <模块名> [新增/修改]

| 功能模块 | 图示 | 详细说明 |
|-----------|------|------|
| 【功能或场景名】 | 图 1：【截图/原型】<br/><br/>位置：【链接或 assets/module-1.png】 | **规则**<br/>1. 在什么条件下发生什么<br/><br/>**状态**<br/>1. 进入、退出和允许的操作<br/><br/>**异常**<br/>1. 失败后停在哪里、用户还能做什么 |

详细说明按业务顺序写。复杂状态可在同一模块下紧接状态表。图文对应；无图时写明缺图。
~~~

## 有内容才加

确认有对应内容时再写入，标题按语义，不补「一、」到「七、」凑齐。飞书里关键关注用红/橙 callout，回归用蓝/灰 callout。

- **关键关注**：复杂协作或跨端风险。写成「关键关注」，列出具体风险。
- **回归范围**：确有要回归的旧能力。写成「回归范围」，分开写需回归和不纳入的范围及原因。
- **Feature List**：模块多于一个、需要总览时。MODULE 列与详情里的 `MODULE-N` 对应。单模块直接写需求详情。
- **关联材料与待确认项**：有原型、设计稿或未确认问题。待确认写具体问题，并说明影响哪条规则。
- **数据观察与发布约束**：有业务指标或影响用户的发布条件。指标写口径；技术埋点放配套材料。没有这些内容时整节不出现。

## 要点

- 写法服从写作规范；旧七章标题只是兼容外壳。
- PM 姓名填版本表 **PM** 列；Agent 不覆盖已有值。
- 版本表只在 `/prd-publish` 成功后追加。版本号从 `1` 起，每次成功发布加 `1`，不写飞书 `revision_id`。第一次的变更内容留空。之后把相对上一份快照的规则差异写入变更内容，飞书这一格用红色文字。本地 `prd.md` 保留「对应 spec / demo」，写入快照相对路径。飞书版本表没有这一列。判断漂移用 `prd.baseline.revision_id`（追加之后的回读 `R2`），不要把 `R1` 或 `R2` 写进版本号，也不要把这段规则写进正文。日常改写不自动追加。旧目录里的 `5-n` / `9-n` 只作历史。
- Feature 的 MODULE 列与需求详情的 `MODULE-N` 一一对应。
- 用户未明确保留时，正文不应残留未决议的 `[待定]` / `[待交互确认]`。
- 连续裸段落 >6 行时，`/prd-check` 只告警不硬拦。`push` 不下这个结论。
- 检查明细写 `prototypes/prd-check-YYYY-MM-DD.md`；基线发布时把结论摘要写入版本表变更内容。
