# PRD AI Review Rubric（9稿）

用于 `/pm-spec`（9稿定稿）的 AI 评审标准：高风险阻断 + 评分反馈 + 可定位改进建议。

> **瘦身前提**：本评审在 Step 4 瘦身之后执行。本地 **不得**再存在讲解层 `narrative.*`（标题含「背景」「价值」的小节，含指针）。「为什么做」以「需求概述」为准。讲解叙事只在飞书；评审不得因本地无背景/价值小节而要求补回。定位见 `prd-feishu-sync/references/chapter-map.md`（语义优先，序号仅兼容）。



落盘分层：

- 详细评审记录写入 `prototypes/ai-review.md`
- `prd.md` 在 **二、版本及进度跟踪** 对应行记结论摘要（如 `AI Review: 可开工`）

## 一、评审范围（先于阻断规则执行）

读取「需求概述」内嵌**开发速览**表中的 **需求类型** 与 **影响范围**，决定深审/轻审范围。

> **注意**：MODULE 标题的 `[新增/修改]` 仅表示**本次 PRD 中的变更模块**，不等于「增量/存量需求」。评审范围由需求类型决定，不由 MODULE 标签决定。

| 需求类型 | 评审模式 | 深审范围 | 轻审/降级 |
|----------|----------|----------|-----------|
| **新增** | 全量 | 所有 MODULE + 需求概述 + 关键关注 + 回归范围 | — |
| **迭代** | 聚焦 | **本轮变更 MODULE 清单**中的 MODULE + 关键关注（必要时核对概述目标句） | PRD 中存在但不在清单中的 MODULE 仅做一致性检查；`影响范围 = 模块` 时复杂流程 Mermaid 可在变更 MODULE 内局部表达 |

**本轮变更 MODULE 清单**（迭代需求在 Step 3 确认，写入 `ai-review.md`）：

1. **首选**：Step 3 脑暴澄清时产品确认的 MODULE 列表
2. **次选**：Feature List 中标注为本次变更的 MODULE
3. **兜底**：以上均缺失 → 全量深审，并在 `ai-review.md` 注明「未提供变更清单，已降级为全量评审」

**评审范围说明**（写入 `ai-review.md` 开头）：

```markdown
## 评审范围
- 阶段：9稿（已瘦身：无 narrative 背景/价值小节）
- 需求类型：<新增 / 迭代> | 影响范围：<页面 / 模块 / 流程>
- 本轮变更 MODULE 清单：<MODULE-2, MODULE-3>
- 深审：MODULE-x, 需求概述, 关键关注, 回归范围
- 轻审：MODULE-z（一致性检查）
```

## 二、阻断规则（P0）

命中任一条即阻断 confirmed：

### 内容质量（7 条）

1. 缺少明确目标或问题定义（以「需求概述」为准：只写「做什么」没写「为什么做」/目标；**不得**要求补写本地讲解层背景/价值）
2. 深审范围内关键 MODULE 缺少可测试验收标准（需求详情说明列验收 checklist）
3. 范围边界冲突或明显自相矛盾
4. 深审范围内关键流程不闭环（成功/失败/异常路径缺失且业务需要）
5. 存在原型引用但路径或锚点无效（有原型需求场景）
6. **9稿残留 `[待定]` 或 `[待交互确认]`**（须于交互评审后消除）
7. **讲解层回流**：本地仍存在 `narrative.*`（标题含「背景」「价值」，含空壳/指针），或为补洞改写「关键关注/回归」展示序号 / 前移四～七

### 可读性结构（3 条）

8. 缺少「关键关注」或「回归范围」小节（按标题关键词定位），或该信息仅出现在版本表 AI Review 摘要之外的无标注区
9. 深审范围内命中复杂流程条件（分支逻辑 / 流程步骤 >= 5）但未提供 Mermaid（迭代+模块级影响时允许在变更 MODULE 详情内局部图示）
10. 存在大段文字违规：连续正文超过 6 行，或虽未超 6 行但主观可读性差

### 用户场景（P0，仅深审 MODULE）

11. 深审范围内 MODULE 的详情说明列完全缺少目标用户与使用场景


## 三、建议项（P1/P2，不阻断 confirmed）

### P1（应修复，扣分并全量列出）

- 有主场景但描述含糊，PM/开发仍可能理解分歧
- 业务需要但缺少边缘/异常场景
- 「回归范围」仅写「无回归」等歧义表述

- 表述、引用、局部可读性可改进但不触发 P0

### P2（可选优化，最多列 3 条）

- 体验优化、表述润色、非关键引用增强

## 四、用户场景透镜（深审 MODULE 必查）

每个**深审** MODULE 的详情说明列须覆盖：


| 要素 | 要求 | 缺失处理 |
|------|------|----------|
| 目标用户 | 一句话（角色/权限/使用前提） | 完全缺失 → P0（规则 11） |

| 核心场景 | 主路径：触发条件 → 用户操作 → 预期结果 | 含糊 → P1 |
| 边缘/异常场景 | 至少 1 条（业务需要时） | 缺失 → P1 |

## 五、评分模型（0-100）

| 维度 | 分值 | 说明 |
|------|------|------|
| 目标与用户场景 | 25 | 仅评深审 MODULE |
| 范围与边界完整性 | 20 | 含关键关注、回归范围 |

| MODULE 结构完整性 | 20 | Feature 清单与详情 MODULE 对齐 |

| 验收标准可测试性 | 20 | |
| 可读性与引用质量 | 15 | |

P1 参考扣分：-8；P2 参考扣分：-3（总分不低于 0）

## 六、输出格式

### 写入 `prototypes/ai-review.md`

```markdown
## 评审范围
（见第一节模板）

## 可开工结论
可开工 / 建议完善后开工 / 不可开工

## 总分
XX/100

## 问题项
### [P0] <类别> — <位置>
...
```

**位置锚点**（语义标题；序号可随模板变化）：

- 需求概述（开发速览；目标/为何做）
- 关键关注 / 回归范围（**不**使用本地讲解层背景/价值）
- 需求详情 / MODULE-N / 说明列 或 图示列



### 写入 `prd.md`

在 **二、版本及进度跟踪** 追加或更新 9稿确认行：`变更内容` 含 `AI Review: 可开工`（或建议完善后开工 / 不可开工）。

## 七、可读性硬约束

- 每份 PRD 须含「关键关注」「回归范围」；回归禁止仅写「无回归」
- 验收标准使用 checklist；MODULE 标题带 `[新增/修改]`
- 复杂流程须 Mermaid（见规则 9）
- 版本表**仅在** 9稿确认时追加 `9-n` 行；日常改写不追加
