# 产品组 PRD 写作规范 V1.0

来源：[产品组 PRD 写作规范 V1.0](https://guanghe.feishu.cn/docx/Cqtqd9BxJoUYAFxbXFocp2qYnWd)

版本：V1.0｜2026-10-16

飞书 `revision_id`：13

本文件是工作区插件编写、更新飞书需求文档正文时的写作规范，也是 AI 生成需求文档的执行依据。

核心要求：业务规则完整、逻辑严密、状态清楚，使用准确、自然、便于协作的产品语言。

## 1. 适用范围与基本原则

本规范用于产品组编写、评审和更新 PRD，也作为 AI 生成需求文档的执行依据。适用于学生端、教师端及配套配置功能；具体章节按需求规模裁剪。

PRD 应让产品、设计和研发对同一场景得到一致理解：用户在什么条件下可以做什么，系统如何处理，最后形成什么结果。

**业务规则完整、逻辑关系明确、状态变化可判定，表达自然准确。**

- 完整性优先于压缩篇幅。适用条件、默认值、分支、状态变化和必要异常不能因追求简洁而省略。
- 用业务语言定义产品行为。展示条件、交互反馈、统计口径和跨端联动写清楚；视觉参数与技术实现分别由设计、研发承接。
- 按功能模块组织需求详情，图示和说明对应。相关规则在同一处讲完整，避免读者跨多处拼接。
- 自然准确的书面表达。句子有明确对象、动作与结果，避免口语碎片、空泛总结和机械模板腔。
- 只写有依据的方案。材料有冲突或规则缺失时，明确待确认问题，不自行补造限制、时长、状态、操作或统计口径。

PRD 正文不单设验收标准章节，不把同一规则改写成验收句再次重复。业务逻辑、状态和异常处理仍须完整写入功能说明；生成过程中的检查由执行 skill 承担。

## 2. 整篇 PRD 的组织方式

默认采用下面的结构。小需求保留必要信息即可，不为了凑齐模板增加空章节；大需求按用户任务和业务模块展开，避免将所有内容塞进一张总表。

| 内容 | 写什么 | 使用要求 |
| --- | --- | --- |
| 标题与版本 | 标题点明对象和变化；有评审或版本迭代时，简记日期、版本及主要改动。 | 避免只写“功能优化”。变更记录概括修改点，不复制聊天过程。 |
| 背景与目标 | 谁在什么场景遇到什么问题，本次要改变什么。 | 通常用一段话讲清现状、问题和预期结果；指标有依据才写。 |
| 本次范围 | 涉及哪些角色、端、业务模块和能力。 | 范围较多时用短清单。只说明容易混淆的范围边界，不罗列大量无关的“不做”。 |
| 需求详情 | 各模块的图示、业务规则、操作逻辑、状态、数据口径及必要异常。 | 正文重点，按第 3、4 节组织。 |
| 关联材料与待确认项 | 原型、设计稿、复用规则的准确出处；尚未确定的具体问题。 | 已有材料直接链接。不留没有内容的章节；关键问题未确认时，不包装为确定结论。 |
| 数据观察与发布约束 | 需要观察的业务指标、触发口径；确有影响的版本、权限或兼容条件。 | 按需增加。技术埋点字段放在配套埋点文档；影响用户行为的发布条件需在对应功能处明确。 |

背景、目标和范围负责说明为什么做、做到哪里；需求详情负责定义具体行为。同一规则只保留一个完整定义位置，其他位置引用模块或条目名称。

## 3. 需求详情的图文与层级

每个功能模块使用独立标题，下面放图文需求表。默认表头为「功能模块／图示／详细说明」。一行承载一个可独立理解的功能或场景。

| 功能模块 | 图示 | 详细说明 |
| --- | --- | --- |
| 简短、具体的功能或场景名称，例如「目录选择与进入」「任务卡片与结果」。 | 放对应的截图或原型。一个操作有多个关键状态时可配多张图，标明各图对应的状态。 | 按该功能的业务顺序写规则。需要对照多个状态或条件时，在同一模块内紧接状态表、条件表或流程说明。 |

**按模块组织，按规则拆分。**

模块优先沿用户任务和业务流程排列。同一模块内先交代适用条件和默认行为，再写主要操作、条件分支和对应异常。页面的上下顺序只用于辅助对照，不应打断业务逻辑。多端协作需说明前一端的动作怎样影响后一端。

**图文必须相互对应。**

图示用于定位页面、操作和状态；文字说明图中看不出的判断条件与处理规则。大图可以按实际场景拆成多张，保留影响理解的上下文。截图不能代替规则，文字也不重复描述整张界面的外观。图文冲突时指出冲突并更新对应材料，不长期以「以文字为准」掩盖差异。

**说明栏使用清楚的段落层级。**

用「选择学科」「提交与统计」「结果展示」等具体名称作加粗小标题，下面逐条写规则。一个编号对应一条主要规则；相关分支紧跟其后。简单功能无需强加小标题，复杂功能不得因表格篇幅而省略状态或例外。

不要求每行套用「功能说明／交互说明／补充规则／验收标准」。不把业务规则、状态和异常集中放到远离功能的文末；跨模块共用规则可以单独定义，并在使用处准确引用。

**按内容密度拆行，保留可读性。**

一个单元格已包含多个独立场景时，应拆行。状态、权限或条件组合较多时，另放一张紧邻的对照表，并在图文表中指向它；避免表格套表格。规则只写一遍，图文表和状态表各自承担不同信息。

飞书单元格中的小标题、规则和子项使用真实段落或原生列表，避免全部挤在一个长文本块里。使用统一编号和术语，不给每句话添加机器编码。无图时明确记录缺图，不用无关图片或臆造截图充数。

## 4. 规则、逻辑与状态必须写清的内容

下表用于检查功能是否写完整，不是要求每个功能都复制九个小标题。涉及的内容必须明确，不涉及的内容不凑数。

| 检查维度 | 应明确的内容 |
| --- | --- |
| 对象与前提 | 谁使用、在哪个端或入口、处理什么业务对象；进入条件、权限和适用范围。 |
| 默认行为 | 首次进入显示什么、默认选中什么、如何排序；返回或再次进入时保留什么、恢复什么。 |
| 操作与结果 | 触发动作、判断条件、处理结果、后续去向；哪些信息新增、更新、保留或清空。 |
| 条件与优先级 | 不同条件分别怎么处理；条件是同时满足还是任一满足；多个条件命中时谁优先，未命中时怎么办。 |
| 状态与变化 | 状态属于哪个对象、各状态的业务含义、进入和退出条件、允许操作及变化后的结果。 |
| 数据与展示口径 | 数据的业务来源、统计范围、分子分母、排序和去重口径；0、缺失、未生成和请求失败如何区别。 |
| 跨页面与跨角色联动 | 教师操作如何影响学生，主页面与详情如何同步；重复打开、切换对象和返回后哪些状态变化。 |
| 异常与边界 | 本功能实际涉及的失败、无权限、无内容、重复操作、中断恢复、超出限制等分支，以及可继续执行的操作。 |
| AI 功能的行为 | 输入范围、输出要求、完成判定；生成中能否继续输入或停止，失败和重试如何处理，历史记录保留什么。 |

### 4.1 规则要能直接作出判断

每条规则应让读者根据给定条件判断结果。复杂逻辑先拆出条件，再写各分支。对「支持」「处理」「保持一致」「按原逻辑」等表述，要补齐对象和边界；复用已有功能时明确复用范围、差异及可定位的出处。

数量、时间、频率和排序要有明确口径：是否包含边界、以哪个业务时间为准、同值如何排序、何时刷新。具体值未经确认，写成待确认问题，不自行填写经验值。

### 4.2 状态需要说明含义、条件和允许操作

先确定状态属于哪个对象，再列状态。作业处理状态、任务列表归类、学生学习进度和界面选中状态应分别说明；「已提交」「批改完成」「学会了」不能互相替代。

对实际存在的状态，说明进入条件、此时显示与允许的操作，以及什么事件使其进入下一状态。存在停止、取消、退回、重试或重新打开时，分别说明规则；没有这些能力时不凭空扩充状态。

表格可按内容选择「当前状态／判定条件／展示与可操作项／触发事件及下一状态」等列。状态组合较多时拆开业务状态和操作流转，避免一张表同时堆积过多维度。只罗列状态名称不算写完整。

### 4.3 例外、联动与数据边界要跟随主规则

失败处理写明失败后停在哪里、原输入和进度是否保留、用户还能做什么。空数据、尚未生成和加载失败分别说明，不能统一写成「暂无」。重复操作是否生效、状态改变后统计是否更新，也应按业务结论明确。

多页面或多角色使用同一结果时，说明更新时机和口径。数字缺失不能自动补 0；完成状态不能由某个结果字段有无反推。确有计算时写公式的业务含义及特殊值处理，不将接口字段表达当作产品定义。

### 4.4 AI 功能需要确定的产品规则

明确哪些内容由配置提供、哪些由模型生成，模型输出怎样影响流程和完成状态；样例回答只是示例时须说明。明确等待、停止、重试、继续对话和历史恢复的规则，以及何时需要用户确认。超时时长、重试次数、模型能力和效果指标都须有依据。

PRD 定义用户可感知的行为与内容要求。提示词、调用链路和模型接口另附材料；不能用「由 AI 判断」代替业务完成条件，也不能因为输出不固定而省略生成中、失败和恢复逻辑。

## 5. 写作语气与内容边界

使用准确、平实的书面中文。先写结论和规则，确有必要时补一句原因。句子有明确主语和动作，同一概念使用同一名称；相关分支就近表达，避免用大量括号补救主句。

不使用「赋能」「形成闭环」「提升体验」等词替代具体变化；避免「按实际情况」「正常处理」「显示相应结果」等无法判断的表述。一般标点按语义使用，不把每条规则都写成分号串，也不把完整逻辑拆成孤立词组。

| 内容 | 正文的写法 | 配套材料承担的内容 |
| --- | --- | --- |
| 视觉与交互 | 写显示条件、用户可用操作、反馈、状态变化和必要提示文案；影响可操作性的遮挡、截断等要说明。 | 颜色、字号、圆角、间距及具体视觉样式由设计稿定义。 |
| 业务与技术 | 写业务数据来源、计算口径、状态含义、更新时机和失败后的行为。 | 接口字段名、数值枚举、数据结构、代码路径和实现方案。 |
| 规则与检查 | 功能规则、分支、状态和必要异常完整写入正文。 | 不生成重复的验收章节；skill 的完整性检查过程不写入业务正文。 |
| 当前方案与讨论 | 写已确认结论；未确认处用明确问题标记，并说明影响哪项规则。 | 讨论过程、废弃方案和机器执行记录按需保留在配套材料。 |

### 5.1 句子改写对照

| 应避免的表达 | 建议写法 |
| --- | --- |
| 构建目录与地图双向联动机制，提升内容触达效率。 | 点击目录中的内容后，地图滑到对应位置并显示入口卡片。 |
| 选中态联动；目录不收起；状态保持。 | 选中内容后，目录保持打开，列表停留在原位置；地图显示对应卡片。 |
| 提交后更新状态，显示相应结果。 | 提交成功后，任务归入「已完成」，卡片显示「批改中」；正式结果生成后，再显示结果摘要。 |
| 异常时按正常逻辑处理。 | 进入失败时，保留目录、选中项、列表位置和入口卡片，显示失败提示，学生可以再次点击。 |
| 当 state=2/3 时显示已完成标签。 | 练习已完成或待批改时，均显示「已完成」。 |
| 卡片高 238px、圆角 17px。 | 视觉规格引用对应设计稿；正文明确卡片信息的显示条件及操作规则。 |

以上为表达方式示例，不是跨功能通用规则。其中「待批改归入已完成」适用于对应来源中的练习口径，其他业务必须单独确认。

## 6. 图文需求示例

以下两个示例取自现有 PRD，按本规范整理。示例只定义所标注的功能范围；其他模块仍按各自需求说明。配图使用原 PRD 截图，演示工具栏及示意数值不作为新增产品要求。插件内不保存截图，图以来源文档为准。

### 6.1 本课目录：选择并进入学习内容

来源：[《学生端-AI 课堂任务体验优化》——目录点击、地图定位与内容进入](https://guanghe.feishu.cn/docx/Mls7d7sAvodUttxQgJec6Zf4nqd)

本例演示目录选择、地图定位和内容进入，目录列表的各类型展示规则不在本例中重复。

图示：选择目录内容后，地图展示对应入口卡片。

**本课目录：选择与进入**

**选择与定位**

1. 点击目录中的一项内容，选中该项并取消原选中项；地图定位到对应节点，显示入口卡片。目录保持打开，列表位置不变。
2. 选择其他环节中的内容时，地图定位到目标路段，顶部环节标识同步变化，整课仍在同一张地图中。
3. 再次点击已选中的内容，保持选中并重新定位对应卡片；不关闭目录，也不直接进入学习页。

**地图与目录的配合**

1. 入口卡片被目录遮挡时，自动调整地图位置，使卡片出现在左侧可见区域。即使节点位于路线首尾，也要保证卡片内容和按钮完整可见。
2. 直接点击地图节点时，显示对应卡片；目录存在对应项时同步选中。目录保持打开，列表位置不变。
3. 上下滑动目录只滚动列表，不触发内容选择；轻触误选某一项时，也不直接进入学习页。

**进入学习与失败处理**

1. 点击入口卡片主按钮后，才进入该内容对应的学习页。各类内容的按钮与进入方式按原文中对应类型规则执行；本例图中的 AI 提问入口为「查看提问」。
2. 进入失败时，保留目录开合状态、选中项、列表位置和地图卡片，沿用对应学习业务的失败提示，可再次点击。
3. 目录和卡片展示一致的学习进度。打开目录、选择内容和定位地图不改变完成状态，不新增观看或作答记录，也不计为学习完成事件。

### 6.2 纸质作业：任务卡片、状态与结果

来源：[《纸质作业学生端》——新版任务卡片与状态、正式结果摘要及首页接入](https://guanghe.feishu.cn/wiki/VJwOw2PgHicZoqkCIrAcOIudnbe)

本例演示任务卡片的状态归类、操作、统计和结果展示。识别检查如何进入补拍、如何重新提交等规则，应在上传与补拍模块定义。

图示：未完成、需补拍、批改中和已完成的任务卡片。

**纸质作业：任务卡片**

**显示范围**

纸质作业展示在新版学生端「全部任务 > 练习」中；开始日期为今天的，同时进入首页今日任务。只展示实际布置给当前学生且其可见的任务。

**提交与统计**

1. 学生提交成功后，任务归入「已完成」，卡片状态显示「批改中」。此时完成的是提交，批改结果可以尚未生成。
2. 提交成功后刷新任务状态，「全部任务」中的该作业从「待完成」更新到「已完成」；属于今日任务的，同时计入今日完成数。
3. 正式结果生成后，卡片显示「已完成」和结果摘要，列表归类继续为「已完成」。
4. 任务是否完成以业务状态为准，不根据得分、正确率或进度反推。结果未返回，不得因此把任务改回「待完成」。

**状态与结果**

各状态的卡片内容和操作见本模块下方状态表；结果摘要的组合与缺失处理见「结果展示规则」。

**状态与操作**

| 当前状态 | 任务列表归类 | 卡片辅助信息 | 按钮及操作结果 |
| --- | --- | --- | --- |
| 未完成 | 待完成 | 截止时间 | 「开始上传」，进入上传页。 |
| 需补拍 | 待完成 | 有效的问题摘要及截止时间，例如「漏拍 2 页｜3 题待处理｜2026/09/20 22:00 截止」。 | 「继续上传」，进入上传页，保留已拍图片、页码和已保存题框。 |
| 批改中 | 已完成 | 「已提交，正在批改」；不展示得分、正确率、错题数和截止时间。 | 「查看」，进入只读原卷结果页。 |
| 已完成 | 已完成 | 正式结果摘要，按下方规则组合。 | 「查看」，进入原卷结果页。 |

**结果展示规则**

1. 老师配置了分值时展示得分，未配置分值时展示正确率。两种情况下，错题数大于 0 才追加「错 N 题」，错题数为 0 时隐藏。
2. 存在待确认题时，在得分或正确率后补充「（N 题待确认）」。待确认题不计入正确率和错题数。
3. 正确率使用正式批改结果，不在卡片中另算口径。结果尚未返回时隐藏对应摘要，不补 0、不展示占位数值。
4. 「需补拍」状态下，漏拍页数或待处理题数为 0 时隐藏对应项；两项均无有效值时，只显示截止时间。

| 条件组合 | 展示示例 |
| --- | --- |
| 有分值，有 2 道待确认题、2 道错题 | 86 分（2 题待确认）｜错 2 题 |
| 无分值，有 2 道待确认题、2 道错题 | 正确率 86%（2 题待确认）｜错 2 题 |
| 有分值，无待确认题、无错题 | 86 分 |
| 已经提交成功，正式结果尚未生成 | 已提交，正在批改 |

示例数值只解释展示组合，不代表固定分数或效果承诺。这里将「批改中」和「任务已完成」分开定义，也将业务状态与结果是否到达分开处理。

## 7. 更新规范与 skill 执行要求

**PRD 更新时维护当前有效结论。**

按本次评审范围修改，保留仍有效的规则。结论变化时同步检查相关图示、条件分支、状态、统计和跨端影响，不只改一个句子。旧规则从当前正文移除或明确失效，必要历史放在变更记录。

复用规则应指向准确的模块或材料。不能只写「同上」「按旧逻辑」而没有可定位的依据；也不把未变化的全部功能复制一遍。待确认项关闭后，结论写回对应功能处。

### 7.1 给研发包装执行 skill

skill 应同时携带本规范、空白结构和确认后的示例。规范控制内容边界与写法，示例用于校准规则颗粒度和阅读感受；不能照搬示例中的具体业务状态、数字或小标题。

| 环节 | 执行要求 |
| --- | --- |
| 输入 | 读取已确认方案、目标范围、原 PRD、截图或原型、相关评审结论。明确哪些是现状、哪些是本次变化、哪些尚未确认。 |
| 规则整理 | 按功能模块梳理前提、默认、条件分支、状态、操作结果、联动和异常；内部保留来源对应关系，不将机器编号批量写进正文。 |
| 缺失与冲突 | 提出具体问题，标明影响的规则；在未确认前保留待确认状态。不能用合理猜测补齐业务决策，也不能擅自增加设计方案。 |
| 成文 | 按规模裁剪整篇结构，图文对应；规则写清，复杂状态用表。文字自然、准确、书面化；保留必要业务名词与界面提示。 |
| 内部检查 | 核对来源覆盖、条件与优先级、状态进入退出、允许操作、成功失败分支、数据口径、跨页面联动和图文一致性。检查过程不生成重复的验收章节。 |
| 写入与回读 | 按用户指定位置写入。飞书表格内使用真实段落、原生列表和对应图片；回读确认标题、段落、表格、图片与文字均实际存在，无遗漏或乱码。 |
| 结果交付 | 提供可访问的文档链接，简述内容；只在存在未解决事项时说明，不附冗长机器执行报告。 |

**执行底线**

禁止把需求改成仅有功能名和口语说明的摘要；禁止为了精简删除状态与异常；禁止以内部检查替代正文中的业务规则；禁止补造未确认方案；禁止把 UI 参数、研发字段和模板套话堆进正文。
