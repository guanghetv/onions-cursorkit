# 三端对齐

原型、飞书需求文档、`prd.md` 是同一需求的三份载体。

## 主路径

先 `/pm-proto` 产出核心页面流程，再 `/pm-spec` 只写本地 `prd.md`。无原型需求可以直接 `/pm-spec`。用户明确说「同步到飞书」时走 `/prd-publish`，不要只 push。

## 任一端先改

写入另外两端之前：

1. 读出三端当前内容。飞书用 `lark-cli docs +fetch`。没有的一端记为缺失。
2. 用一段判断说明差异：哪一端更新、影响哪些模块、建议如何写回另外两端。
3. 用户明确确认前，不写另外两端。
4. 确认后只改用户同意的那一端或两端。飞书文档已有内容时禁止整篇覆盖。

## 何时提示、何时写回

每一轮 `/pm-spec` 和每一次 `/pm-proto` 开始时都要做上面的差异提示。用户这一轮只确认改 `prd.md` 或只改原型时，不写另外两端。

用户明确说「同步到飞书」或「推到飞书」时，执行 `/prd-publish`。不要只 push。预检、写入、校验和基线都在发布流程里。

`/prd-publish` 会把当前 `prd.md` 推到飞书并钉基线。飞书只是落后于 `prd.md` 时直接写入。原型或飞书有 `prd.md` 里没有的更新时，先展示差异，用户确认仍按当前 `prd.md` 发布后才写。

## 飞书先改、贴回工作区

产品先在飞书里改了文档，再把链接或正文贴进会话，要求更新本地时：

1. 先 Read 本文件，再走「任一端先改」。
2. 用绑定文档的 `doc_token` 做 `lark-cli docs +fetch`。聊天粘贴的正文只当线索，不能代替 fetch。
3. 同时读 `prd.md` 和原型，展示差异与建议写回项。
4. 用户确认前，不改 `prd.md`，不改原型，也不用本地旧稿 `push` 盖掉飞书手改。
5. 确认后只写用户同意的本地或原型差异。随后把 `metadata.consistency.status` 标成 `unknown`。若写了本地契约，飞书文末「文档状态」重置为未校验态：emoji `📎`、`background-color="light-blue"`、`border-color="blue"`、校验行「未校验」。不要只改文字，不要写成通过。不跑 `/prd-check`，不写基线。

正式入口是 `/prd-feishu-sync reconcile`（或 `pull`）。用户没说命令名、只贴了链接要求同步回来时，同样按本条执行，不要直接整篇覆盖 `prd.md`。

## 草稿超前，还是另一端多了内容

不要用 `feishu.last_synced_at` 单独判断手改。草稿期本地 `prd.md` 本来就会新于飞书。

**草稿超前：** 飞书没有当前 `prd.md` 里没有的契约，原型也没有当前 `prd.md` 里没有的流程或锚点。本地只是还没推上去。

- `/pm-spec` 下一轮用一句话说明飞书仍是旧的，继续改本地，不阻断。
- `/prd-publish` 这次命令就是同意按当前 `prd.md` 发布，直接写入飞书，不再追问。
- 已有基线且本地正文偏离快照时，发布结果里写明「相对上一版基线有未发布改动」。这是告知，不是第二道确认。只多出版本表那一行不算偏离。

**必须停下：** 飞书或原型有当前 `prd.md` 没有的内容。先展示差异。用户确认「仍按当前 `prd.md` 发布」，或先 reconcile / 改原型之后，才能写另外一端，也不能用本地旧稿把飞书手改盖掉。

`/prd-check` 单独跑时，另一端多出来的内容写进检查结果，不因为本地只是超前就先停下来不查。

## 怎样算漂移

同时看两处，有一处不同就是漂移：

- 飞书当前 `revision_id` 不等于 `prd.baseline.revision_id`。这个序号是 `/prd-publish` 最后一次写完飞书之后的回读，不是版本表单元格里的 `R1`。
- 当前 `prd.md` 的需求正文与 `prd.baseline.snapshot` 不一致。只多了发布时追加的版本表行，不算漂移。

没有基线时，除 `/qa-spec` 外的下游不把当前正文当作已发布需求。

## 下游怎么读

除 `/qa-spec` 外，开发在漂移或尚未第一次发布时，读 `prd.baseline.snapshot`。没有快照时停止并说明尚未发布，不改用当前 `prd.md`。

未漂移时读当前 `prd.md`。

`/qa-spec` 仍生成用例。已发布且未漂移时读当前 `prd.md`；用户同时给出飞书链接时读飞书当前正文。已漂移且有快照时读快照并提示。尚未发布或没有快照时读当前正文并提示风险。只有来源已发布、未漂移，且 `consistency.status` 为 `pass` 或 `warn` 时，才把 `test_spec.status` 写成 `confirmed`。缺失或 `unknown` 保持 `pending`。
