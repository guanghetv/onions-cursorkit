# Verify Change

本技能用于 Tier 2+ 的验证阶段。目标是把测试、静态对照、浏览器验证和归档判断沉淀到 `e2e-report.md`。

## 输入

- 当前 `openspec/changes/<change-id>/`。
- `proposal.md`
- `specs/**/spec.md`
- `tasks.md`
- `backend-*.md`（如有）
- `qa-*.md`（如有）
- 用户提供的环境、账号、URL 或手动验收结果。

## 验证依据优先级

1. `qa-*.md`：测试/QA spec，优先级最高。
2. `specs/**/spec.md`：OpenSpec 行为场景。
3. `backend-*.md`：接口、错误码、数据结果辅助。
4. `proposal.md`：目标、范围、不做范围和风险说明。

如 QA spec 与其它产物冲突，必须在报告中显著标注，不能默认以前端或实现为准。

## 步骤

1. 定位 change-id；多个候选时请用户选择。
2. 读取验证依据，生成场景清单。
3. 先做 TDD / 静态验证记录：
   - 有测试命令则运行或记录结果。
   - 无测试工具时明确写“未配置 / 未执行”，不得虚构。
   - 静态对照接口、文案、状态、权限、错误码。
4. 展示清单摘要，询问用户是否执行浏览器自动化。
5. 用户同意后，使用当前环境可用的内置浏览器能力执行；缺账号、验证码、SSO 或权限时停止并记录 blocker。
6. 写入或更新 `e2e-report.md`。

## Browser 自动化约束

- 进入浏览器自动化前，必须先输出验证清单摘要，包含依据来源、必跑场景、TDD/静态检查状态和已知 blocker。
- 用户未明确同意前，不调用浏览器自动化工具。
- 自动化优先使用产品内置浏览器能力（如会话中暴露的 browser/cursor-ide-browser 工具）。用户自行配置的 Chrome DevTools MCP 或类似工具不是默认执行通道，除非用户明确要求。
- 缺少 URL、账号、登录态、环境或权限时，引导用户在浏览器中手动登录并导航到待验收页面；用户确认就绪后再接管。
- 每个场景应记录操作、观察结果和证据；无法自动化的步骤写成手动验收结果，不得虚构已执行。

## e2e-report.md 模板

```markdown
# E2E Report: <change-id>

## 验证范围

- 依据: <qa-spec / OpenSpec / backend spec / 用户验收>
- 场景数: <N>
- 执行时间: <YYYY-MM-DD HH:mm>

## 验证清单结论

- TDD / 静态检查: <通过 / 失败 / 未配置 / 未执行>
- 文档对照: <一致 / 有差异 / 有冲突>
- 浏览器验证: <通过 / 失败 / 未执行>

## 与 QA spec 的显著差异

| QA 预期 | 当前实现或其它 spec | 结论 |
|---------|----------------------|------|
| <无则写无> | | |

## 通过

- <场景、证据、截图或命令>

## 失败

- <场景、期望、实际、证据>

## 阻塞项

- <账号、环境、权限、数据、外部依赖；无则写无>

## 验收结论

- 结论: <通过 / 不通过>
- 阻塞项: <无 / 列表>
- 归档建议: <可归档 / 先修复并重跑 / 需用户确认带债>
```

## 归档门禁

- 默认只有 `结论: 通过` 且 `阻塞项: 无` 时提示可归档。
- `结论: 不通过` 时，必须先修复并重跑。
- 仅当用户明确同意带债归档，且报告写明同意时间与已知问题摘要时，才可提示带债归档。
- `/onion-finish` 以 `## 验收结论` 为判读入口。

## 停止条件

- 缺少验证依据且用户无法提供。
- QA spec 与实现冲突未裁决。
- 浏览器自动化需要登录、验证码或权限，用户未准备环境。
- Tier 2+ 试图跳过 E2E 且没有等价验收证据。
