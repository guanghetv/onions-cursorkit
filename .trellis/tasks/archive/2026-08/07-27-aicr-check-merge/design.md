# AICR 前移到 check 阶段技术设计

## 一、改动落点

只改 Onion SDD 一层，全部是文档与规则：

| 位置 | 改动 |
|---|---|
| `plugins/onion-sdd/rules/onion-sdd.mdc` | 审查章节重写：check 四步顺序、暂存范围、授权边界、提交门禁条件化 |
| `plugins/onion-sdd/skills/full-change`、`auto-flow` | check 阶段口径 |
| `plugins/onion-sdd/commands/onsf-continue.md` | check 路由 |
| `plugins/onion-sdd/README.md`、`USAGE.md`、`docs/**` | 用户文档口径 |
| `.trellis/spec/**` | 回写与本次冲突的旧约定 |

`plugins/common/**`、`.claude/skills/trellis-check/SKILL.md`、`.trellis/scripts/**` 零改动。

## 二、核心决定：基线统一为暂存区

`aicr-local` 的 `staged` 模式读 `git diff --cached`。把 check 阶段的审查基线也定为暂存区，带来三个直接好处：

1. `/cr` 原样调用，不需要覆盖它的任何步骤，也不需要在 onion-sdd 侧复述它的规范清单或报告格式。
2. 审查对象就是最终提交物，语义准确。
3. 常规路径只审一遍。提交门禁在暂存区未变时直接放行。

代价是 check 不再纯只读——它会 `git add`。这一点已确认接受，边界见第四节。

曾考虑过的替代方案是给 `aicr-local` 加工作区模式、或在 onion-sdd 侧覆盖其步骤 1 读工作区 diff。前者超出「只改 onion-sdd」的范围；后者会让 CR 基线（工作区）与提交物（暂存区）不一致，从而必须在提交时再审一遍，正是要消除的重复。

## 三、check 阶段四步

```text
实现完成
  → 1. trellis-check 子代理（lint / typecheck / 测试 / .trellis/spec 对齐 / spec 回写）
       含其自身的问题修复
  → 2. 暂存本次 change 范围内的改动
  → 3. /cr 审查暂存区
  → 4. 有问题 → 修复 → 重跑受影响的门禁 → 重新暂存 → 复审，循环至通过
  → integrate / verify
```

### 修复循环要回跑门禁

第 4 步的修复可能破坏第 1 步已通过的检查。CR 提的不都是格式建议——「抽成共享常量」「补边界判断」这类会真改逻辑，改完测试可能挂、类型可能不过。

因此循环里要判断修复的性质：纯格式或命名调整直接重新暂存复审；触及逻辑的修复要重跑相关的 lint / typecheck / 测试再暂存。不要求每次都全量重跑 `trellis-check`，按修复影响面选。

### 顺序不可调换

`trellis-check` 会修改代码（修 lint、补测试）。若先暂存再跑它，它的修复落在工作区而不在暂存区，`/cr` 审到的就是未修复版本，且最终提交物与审查对象脱节。

这是本设计最容易实现错的一点，规则里要显式写出理由，不能只写顺序。

### 为什么 CR 由主会话执行

`trellis-check` 以子代理派发，`/cr` 由主会话在子代理返回后调用。不把 CR 塞进子代理提示词：子代理按自己的 `SKILL.md` 走固定步骤，注入外部流程会让两套步骤交错，且子代理输出无法被编排层单独取用。

### 职责切分是弱约束

派发 `trellis-check` 时可声明「人工 review 维度由后续 `/cr` 覆盖，不必展开」，但它仍会按自己的 `SKILL.md` 走 Step 4 / Step 5。实际效果是减少重复输出，不是杜绝。合并结论时去重即可——重叠比遗漏安全。不要为此改 Trellis 源码。

## 四、暂存范围与授权边界

### 范围

只暂存属于本次 change 的改动。判断依据是本次实现实际触及的文件与 `tasks.md` 对应的产物。

不使用 `git add -A`：用户工作区常有与本次 change 无关的本地改动（调试代码、个人配置、其它分支遗留），全量暂存会把它们卷进审查和后续提交。

归属存疑的文件列清单请用户确认，不默认纳入。这是唯一需要用户介入的点，且只在存疑时出现。

### 暂存区已有内容

用户可能在 check 之前手动暂存过其它内容。处理原则是**只增不减**：提示用户暂存区含本次 change 之外的内容，但不执行 `git reset`。

移除他人已暂存的内容是真正的破坏性操作——用户可能正在攒一个精确的提交，`git reset` 之后那个意图就丢了，且无法从 reflog 恢复暂存状态。多审几个文件无害，擦掉用户的暂存意图有害。

### 授权边界

| 动作 | check 阶段 | 依据 |
|---|---|---|
| `git add`（限本次 change） | 允许自动 | 可逆，`git reset` 即可撤销 |
| `/cr` | 允许自动 | 只读 |
| `git commit` | **禁止**自动 | 写入历史，撤销成本高 |
| push / PR / MR | **禁止**自动 | 影响他人，不可逆 |

放宽的是 `git add`，不是提交。规则里这两条要分开写，避免被理解成「check 阶段可以自动提交」。

`/onsf-auto` 同样适用：暂存与 CR 可自动执行，遇到 commit 仍按既有高风险清单停止。

## 五、提交门禁条件化

```text
用户授权提交
  → 暂存区自 CR 通过后未变化 → 直接 commit
  → 有任何变化（含新增暂存文件）→ 重新 /cr → commit
  → 无法判定 → 按重审处理
```

判定由 Agent 依据会话内上下文完成，不引入指纹机制、不修改 `onion_state.py`。跨会话时上下文丢失，按「无法判定」重审——这是安全的默认，代价只是多审一次。

判定必须覆盖**新增暂存文件**，不能只看「代码有没有改」。用户在 CR 通过后又 `git add` 了别的文件，那部分从未被审过，是唯一的漏审入口。

## 六、降级

| 场景 | 行为 |
|---|---|
| `/cr` slash command 不可用 | 读取并按 `aicr-local` 的 `SKILL.md` 审查暂存区 |
| `aicr-local` 未安装 | Agent 对暂存区自审，注明团队规范维度未覆盖 |
| 暂存后暂存区为空（无本次 change 改动） | 输出提示并跳过 CR |
| Trellis 不可用 | check 退化为项目可用的 lint / 测试 / OpenSpec 对照，CR 段仍可独立执行 |

前两条与现行规则第 91–92 行完全一致，直接复用，不需要新写降级逻辑。

## 七、兼容性

`aicr-local`、`/cr` 与提交门禁的既有行为不变。`fe-specflow` / `be-specflow` 也在提交边界用 `staged` 模式调 `/cr`，同样不受影响。本次改动对 Onion SDD 之外的所有流程零感知。

只发 `plugins/onion-sdd` 一个插件，`plugins/common` 不动版本。

## 八、回滚

撤掉规则与技能中的 check 阶段 CR 描述，并把提交门禁恢复为无条件审查，即回到现状（归档任务 `07-17-onion-aicr-gate` 的形态）。纯文档还原，无状态迁移、无跨插件依赖、无数据兼容问题。
